# Сохранение ресурсов и дисковых лимитов

```bash
cd /root/Hosting
git pull
docker compose up -d --build backend worker frontend
```

После обновления перезагрузите страницу панели. Выберите значения и нажмите
«Сохранить настройки ресурсов»; само движение ползунка ничего не сохраняет.
Периодический опрос статуса не должен сбрасывать несохранённые изменения.
CPU/RAM отправляются валидным Merge Patch и сохраняются в БД вместе с
дисковыми лимитами. После повторного открытия страницы используются
сохранённые значения, а не случайные значения по умолчанию.

Для изменения CPU/RAM у уже запущенной ВМ нажмите Stop, дождитесь остановки
и нажмите Start. Перезагрузка внутри гостевой ОС не пересоздаёт VMI и не
заменяет его конфигурацию. Такая остановка вызывает простой приложения.

## Размер диска

Диск определяется по ссылке в текущем манифесте, включая `restore-…-disk-0`
после S3-отката. ISO, старые диски и резервные копии по совпадению имени
не выбираются. Уменьшение логического размера запрещено; файловый overhead
CDI не вычитается путём уменьшения PVC.

Для обычного роста PVC нужны поддержка драйвером и `allowVolumeExpansion`
у класса хранения — см. [Kubernetes volume expansion](https://kubernetes.io/docs/concepts/storage/persistent-volumes/#expanding-persistent-volumes-claims).
У стандартного `rancher.io/local-path` нет такого механизма — см.
[задачу поддержки расширения local-path](https://github.com/rancher/local-path-provisioner/issues/190).
Ошибка расширения показывается в панели; настройки CPU/RAM и лимитов можно
сохранить отдельно, оставив размер диска прежним. Автоматического переноса
дисков в другой класс хранения в этом обновлении нет. Даже при успешном
увеличении PVC может потребоваться расширение раздела/файловой системы
внутри гостя; перед такими действиями проверьте резервную копию.

## IOPS и МБ/с

Worker периодически читает настройки из БД, в том числе после своего
рестарта, и применяет их к cgroup текущего пода работающего VMI. Нулевое
значение снимает предыдущий лимит. Устройство берётся с активного PV
или CSI-mount, а не с общего пути хранилища k3s. Раздел сопоставляется
с целым блочным устройством. Для нескольких дисков на одном устройстве
ограничение суммарное; для разных устройств применяется к каждому.

Нужны cgroups v2 и доступный `io.max` в cgroup пода. Worker не включает
контроллеры в иерархии хоста автоматически. Недоступный контроллер, устройство
или отказ записи выводятся в журнал:

```bash
cd /root/Hosting
docker compose logs --since 10m --tail 200 worker
```

Значения в панели — сохранённые настройки, не подтверждение измеренной
скорости. Лимиты относятся к фактическому блочному I/O: чтение из кеша и
кратковременные всплески нельзя использовать как единственный тест.
См. [Linux cgroups v2 I/O controller](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#io).
Файловые системы без блочного устройства (например, NFS) не поддерживаются
этим механизмом; проверка скорости на реальном хосте обязательна.
