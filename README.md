## 1. Архитектура системы

Платформа спроектирована как двухкомпонентная система: **Панель управления (Бэкенд FastAPI + Фронтенд React)** и **Гипервизор виртуализации (Kubernetes K3s + KubeVirt)**.

```
+-------------------------------------------------------------------------------------------------+
|                     ФИЗИЧЕСКИЙ / ВИРТУАЛЬНЫЙ ХОСТ (VMware / Dedicated / VPS)                    |
|                                                                                                 |
|   +--------------------------+                         +------------------------------------+   |
|   |    CONTAINER (PORT 8080) |                         |    CONTAINER (PORT 8000)           |   |
|   |    hosting-frontend      |                         |    hosting-backend                 |   |
|   |    (Nginx + React SPA)   | --[ Proxy REST/WS ]---> |    (FastAPI, Python, Client SDK)   |   |
|   +--------------------------+                         +------------------------------------+   |
|                 |                                                        |                      |
|           [ HTTP/WS ]                                            [ K8s API Client ]             |
|                 v                                                        v                      |
|   +-----------------------------------------------------------------------------------------+   |
|   |                               KUBERNETES K3S SINGLE-NODE CLUSTER                        |   |
|   |                                                                                         |   |
|   |   +------------------+     +--------------------+     +-------------------+             |   |
|   |   | KubeVirt Operator|     | CDI Operator       |     | Multus CNI        |             |   |
|   |   | (virt-handler)   |     | (DataVolume/PVC)   |     | (macvlan bridge)  |             |   |
|   |   +------------------+     +--------------------+     +-------------------+             |   |
|   |            |                         |                          |                       |   |
|   |            v                         v                          v                       |   |
|   |   +-------------------------------------------------------------------------------+     |   |
|   |   |                           KUBEVIRT VIRTUAL MACHINE POD                        |     |   |
|   |   |                           (virt-launcher-test-vm)                             |     |   |
|   |   |                                                                               |     |   |
|   |   |   +-----------------------+   +-------------------+   +-------------------+   |     |   |
|   |   |   |       vNIC eth0       |   |     vNIC eth1     |   |  vHDD (qemu/kvm)  |   |     |   |
|   |   |   |  (Masquerade Pod Net) |   |  (Home Bridge Net)|   |  (Persistent PVC) |   |     |   |
|   |   |   +-----------------------+   +-------------------+   +-------------------+   |     |   |
|   |   +-------------------------------------------------------------------------------+     |   |
|   +-----------------------------------------------------------------------------------------+   |
+-------------------------------------------------------------------------------------------------+
```

### Ключевые компоненты:
1. **K3s:** Легковесный дистрибутив Kubernetes от Rancher. Мы отключаем дефолтные `traefik` (Ingress) и `servicelb` (LoadBalancer) во избежание захвата портов и лишнего потребления RAM.
2. **KubeVirt:** Превращает Kubernetes в традиционный гипервизор. Он запускает QEMU/KVM-виртуализацию внутри Kubernetes-подов. Процесс виртуализации изолирован в контейнере `virt-launcher`.
3. **CDI (Containerized Data Importer):** Сервис для подготовки и загрузки дисков виртуальных машин. Он автоматически создает Persistent Volume Claim (PVC), скачивает в него ISO или QCOW2 образ по HTTP/S3/Registry и конвертирует его в сырой дисковый файл.
4. **Multus CNI:** Позволяет подключать поды к нескольким сетям одновременно. В нашей системе виртуалка имеет два сетевых интерфейса:
   * `default` (masquerade): Системная сеть Kubernetes, используемая для связи с API-сервером и внешним миром.
   * `bridge-net` (macvlan): Мост поверх сетевой карты хоста. Позволяет виртуалкам находиться в одном L2-сегменте с вашей домашней сетью и получать IP от роутера.

## 2. Подготовка гипервизора (VMware / Dedicated / VPS)

В зависимости от того, где развернута ваша основная нода Ubuntu (гипервизор), требования к настройке виртуализации и сети будут отличаться. Выберите ваш вариант ниже:

---

### Вариант А: Виртуальная машина в VMware (Локальная сеть / Домашний стенд)

Поскольку ваша нода Ubuntu сама запущена внутри VMware, необходимо разрешить передачу трафика от гостевых систем с собственными MAC-адресами (для работы Multus CNI) и активировать вложенную виртуализацию.

#### Шаг A.1: Вложенная виртуализация (Nested Virtualization)
1. Полностью выключите виртуалку Ubuntu в VMware.
2. Откройте **Edit Virtual Machine Settings** (Изменить настройки виртуалки).
3. Перейдите в раздел **Processors** (Процессоры).
4. Установите галочку на пункте **"Virtualize Intel VT-x/EPT or AMD-V/RVI"** (Виртуализировать Intel VT-x/EPT или AMD-V/RVI).
5. Нажмите **Save** (Сохранить) и запустите виртуалку.

> [!IMPORTANT]
> Без этого шага KubeVirt переключится в программную эмуляцию (QEMU TCG), что снизит производительность процессора и дисков гостевых систем в 20–50 раз.

#### Шаг A.2: Настройка VMware Virtual Switch (для работы Моста/DHCP)
Виртуальный коммутатор VMware по умолчанию блокирует трафик от MAC-адресов, которые не принадлежат основной виртуалке. Так как ВМ KubeVirt будут генерировать свои MAC-адреса для получения IP от вашего домашнего роутера через `macvlan`, измените политику безопасности:

1. Откройте ESXi Web Client или настройки VMware Workstation.
2. Перейдите в **Virtual switches** (Виртуальные переключатели) -> выберите используемый коммутатор (например, `vSwitch0`) или настройте конкретную порт-группу (например, `VM Network`).
3. Перейдите в раздел **Security** (Безопасность) и установите следующие параметры в положение **Accept** (Принять):
   * **Promiscuous mode** (Неразборчивый режим): **Accept**
   * **MAC address changes** (Изменение MAC-адресов): **Accept**
   * **Forged transmits** (Поддельные передачи): **Accept**
4. Сохраните настройки.

### Вариант Б: Выделенный сервер (Dedicated Server / Bare Metal)

Если вы арендуете физический сервер без систем виртуализации (в дата-центрах Hetzner, OVH, Leaseweb и др.):

#### 1. Аппаратная виртуализация
По умолчанию на выделенных серверах аппаратная виртуализация (Intel VT-x или AMD-V) включена в BIOS. Проверьте её доступность на сервере:
```bash
ls -la /dev/kvm
# Вывод должен быть похож на: crw-rw----+ 1 root kvm 10, 232 ... /dev/kvm
```
Если файла `/dev/kvm` нет, зайдите в BIOS/IPMI сервера и включите параметры **Virtualization Technology (VT-x)** и **Direct I/O (VT-d)**.

#### 2. Сетевая конфигурация у хостинг-провайдеров (Проблема MAC-адресов)
Большинство дата-центров (например, Hetzner, OVH) блокируют любые чужие MAC-адреса на порту свитча из соображений безопасности. Дефолтный `macvlan` мост работать **не будет**, так как виртуалки не смогут общаться с сетью.

У вас есть два пути решения:

* **Способ 1: Дополнительные IP с привязкой виртуальных MAC (Рекомендуемый)**
  1. Купите у провайдера дополнительные IP-адреса (Failover IP / Additional IP).
  2. В личном кабинете хостинга (например, Hetzner Robot или OVH Manager) для каждого дополнительного IP сгенерируйте **Виртуальный MAC-адрес (Virtual MAC)**.
  3. При создании виртуальной машины в панели управления обязательно укажите этот сгенерированный MAC-адрес в настройках сетевого интерфейса.
  4. Внутри самой гостевой ОС настройте сетевой интерфейс статически, указав купленный IP, маску и шлюз, выданные провайдером.

* **Способ 2: Настройка Routed Bridge (Маршрутизируемый мост)**
  Если провайдер выдал вам целую подсеть (например, `/29`), но без возможности генерации MAC-адресов:
  1. Вместо `macvlan` CNI настраивается стандартный Linux `bridge` (например, `br0`), который **не** привязан к физическому интерфейсу напрямую.
  2. На хосте включается IP Forwarding: `sysctl -w net.ipv4.ip_forward=1`.
  3. IP-адрес моста на хосте настраивается как шлюз для подсети.
  4. На основном сетевом интерфейсе настраивается маршрутизация (Proxy ARP или статические маршруты через шлюз провайдера).
  5. В манифесте Multus CNI прописывается тип `bridge` с указанием созданного `br0`.

### Вариант В: Виртуальный сервер (VPS / VDS) в облаке

Если вы разворачиваете платформу на виртуальном сервере в облаке (Hetzner Cloud, DigitalOcean, Yandex Cloud, Selectel, AWS, GCP и т.д.):

#### 1. Вложенная виртуализация (Nested Virtualization)
Большинство облачных провайдеров на стандартных тарифах отключают вложенную виртуализацию. Проверьте её статус:
```bash
egrep -c '(vmx|svm)' /proc/cpuinfo
```
* Если результат **больше 0** — вложенная виртуализация поддерживается.
* Если результат **0** — аппаратное ускорение недоступно.
  > [!TIP]
  > Наш скрипт автоматической настройки `bootstrap-host.sh` определит отсутствие `/dev/kvm` и автоматически пропатчит KubeVirt для работы в режиме **программной эмуляции** (`useEmulation: true`).
  > Виртуалки запустятся и будут полностью дееспособны, но скорость работы процессора и дисков снизится. Для продакшена рекомендуется выбирать VPS с поддержкой Nested Virtualization (например, Bare Metal инстансы или специальные тарифы с nested-режимом).

#### 2. Обход ограничений сети в Облаке (Masquerade / NAT)
В облачных VPS невозможно использовать `macvlan` или классический мост, так как провайдеры жестко фильтруют трафик на уровне гипервизора: пакеты с любыми MAC/IP, отличными от выданных вашей VPS, мгновенно сбрасываются.

**Решение: Использование сети Masquerade (встроенный NAT KubeVirt)**

На VPS виртуалки запускаются без использования Multus CNI. Сетевой интерфейс настраивается через механизм **Masquerade**:

1. Виртуалка получает внутренний IP-адрес из CIDR Kubernetes-подов.
2. Доступ в интернет из виртуалки работает автоматически через NAT (IP-адрес вашей VPS).
3. **Для внешнего доступа (SSH, RDP, Web-сервисы):**
   Порты виртуалки пробрасываются наружу с помощью Kubernetes-сервиса типа `NodePort`.

   *Пример манифеста для проброса SSH (порт 22) гостевой виртуалки на порт 30022 вашего VPS:*
   ```yaml
   apiVersion: v1
   kind: Service
   metadata:
     name: vm-ssh-portforward
     namespace: default
   spec:
     ports:
     - port: 22
       protocol: TCP
       targetPort: 22
       nodePort: 30022 # Порт, по которому виртуалка будет доступна на IP хоста
     selector:
       kubevirt.io/domain: name-of-your-vm # Имя вашей ВМ в Kubernetes
     type: NodePort
   ```
   После применения этого манифеста (`kubectl apply -f service.yaml`) вы сможете подключиться к виртуалке из интернета по адресу:
   ```bash
   ssh root@<IP_АДРЕС_ВАШЕГО_VPS> -p 30022
   ```

4. **Работа панели в режиме VPS:**
   * **VNC / noVNC:** Работает "из коробки" без дополнительных настроек сети, так как веб-консоль проксирует трафик через Kubernetes API WebSocket, минуя внешние IP виртуалки.
Перед началом установки необходимо подготовить операционную систему Ubuntu (версии 22.04 LTS или 24.04 LTS) на вашем сервере. Этот шаг обновит все пакеты безопасности и склонирует исходный код проекта.

Выполните следующие команды в терминале вашего сервера:

### Шаг 3.1: Обновление пакетной базы и установленных пакетов
Сначала обновите списки пакетов из репозиториев и установите последние версии всех системных компонентов:
```bash
sudo apt update && sudo apt upgrade -y
```

### Шаг 3.2: Установка Git и базовых системных зависимостей
Убедитесь, что в системе установлен Git для клонирования проекта, а также curl и другие системные пакеты:
```bash
sudo apt install git curl software-properties-common apt-transport-https ca-certificates -y
```

### Шаг 3.3: Клонирование репозитория проекта
Клонируйте официальный репозиторий проекта в домашнюю директорию вашего пользователя:
```bash

```

### Шаг 3.4: Переход в директорию проекта

```bash

```

## 4. Развертывание кластера (Скрипт Bootstrap)

Мы подготовили автоматизированный скрипт [bootstrap-host.sh](file:///Users/vladislavkarasev/Documents/Хостинг/scripts/bootstrap-host.sh), который настраивает хост-систему с нуля.

### Что делает скрипт пошагово:
1. **Проверка прав и архитектуры:** Убеждается, что скрипт запущен от `root`. Проверяет наличие файла `/dev/kvm`. Если KVM отсутствует (не выполнена настройка в VMware), скрипт выведет предупреждение и пропатчит KubeVirt для работы в режиме эмуляции.
2. **Определение сетевого интерфейса:** Находит сетевую карту с дефолтным шлюзом (например, `ens33` или `eth0`).
3. **Установка системного софта:** Устанавливает `curl`, `jq`, `iptables`, `bridge-utils` для сетевой конфигурации.
4. **Установка K3s:** Вызывает официальный скрипт установки K3s с параметрами отключения Traefik и ServiceLB.
5. **Настройка прав Kubectl:** Копирует файл конфигурации `/etc/rancher/k3s/k3s.yaml` в домашний каталог текущего пользователя (`~/.kube/config`) и выдает права.
6. **Установка Multus CNI:** Применяет DaemonSet Multus CNI. Создает ресурс `NetworkAttachmentDefinition` с именем `bridge-network`, который настраивает CNI-драйвер `macvlan` в режиме `bridge` поверх вашей активной сетевой карты.
7. **Установка KubeVirt:** 
   * Запрашивает через GitHub API релиз стабильной версии.
   * Устанавливает KubeVirt Operator.
   * Разворачивает KubeVirt Custom Resource (CR) с запуском всех необходимых контроллеров.
   * При отсутствии KVM активирует режим эмуляции (`useEmulation: true`).
8. **Установка CDI:**
   * Скачивает и устанавливает CDI Operator.
   * Создает CDI Custom Resource для развертывания DataVolume импортера.
9. **Установка virtctl:** Скачивает бинарный файл virtctl под архитектуру процессора сервера (amd64/arm64) и помещает в `/usr/local/bin/virtctl`.

### Запуск скрипта:
```bash
# Перейдите в папку со скриптом
cd Hosting/scripts

# Сделайте его исполняемым
chmod +x bootstrap-host.sh

# Запустите установку
sudo ./bootstrap-host.sh
```

### Проверка успешности установки:
Выполните команду проверки подов:
```bash
kubectl get pods -A
```
*Ожидаемый вывод:*
* В неймспейсе `kubevirt` должны быть запущены: `virt-api`, `virt-controller`, `virt-handler` (на каждой ноде), `virt-operator`.
* В неймспейсе `cdi` должны быть запущены: `cdi-api`, `cdi-controller`, `cdi-deployment`, `cdi-operator`.
* В неймспейсе `kube-system` должны быть запущены поды `kube-multus-ds-*`.

## 5. Запуск панели управления (Docker Compose)

Панель управления разворачивается локально с помощью Docker Compose.

### Конфигурация [docker-compose.yml](file:///Users/vladislavkarasev/Documents/Хостинг/docker-compose.yml):
```yaml
version: '3.8'

services:
  backend:
    build:
      context: ./backend
      dockerfile: Dockerfile
    container_name: hosting-backend
    network_mode: host
    restart: unless-stopped
    volumes:
      - /etc/rancher/k3s/k3s.yaml:/root/.kube/config:ro
      - /var/run/docker.sock:/var/run/docker.sock:rw
      - ./data/images:/app/data/images:rw
    environment:
      - PORT=8000
      - HOST=0.0.0.0
      - IMAGES_DIR=/app/data/images
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"

  frontend:
    build:
      context: ./frontend
      dockerfile: Dockerfile
    container_name: hosting-frontend
    network_mode: host
    restart: unless-stopped
    depends_on:
      - backend
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"
```

### Почему используется `network_mode: host`?
1. **Доступ к K3s API:** API сервер Kubernetes по умолчанию привязан к `127.0.0.1:6443`. Использование хост-сети позволяет контейнеру бэкенда обращаться к API-серверу напрямую по localhost без перенастройки сертификатов кластера.
2. **Проксирование WebSocket:** Nginx во фронтенде проксирует WebSocket-запросы VNC консоли на бэкенд на `127.0.0.1:8000`. В режиме host-сети этот процесс не требует внешних мостов Docker.

### Сборка и запуск контейнеров:
```bash
# Перейдите в директорию с файлом docker-compose.yml
cd Hosting

# Запустите сборку и старт в фоновом режиме
sudo docker-compose up -d --build
```
После успешного запуска:
* Панель управления (фронтенд) доступна по адресу: `http://IP_ВАШЕГО_СЕРВЕРА:8080`
* REST API бэкенда доступно по адресу: `http://IP_ВАШЕГО_СЕРВЕРА:8000`

## 6. Подробное руководство пользователя по функциям

Платформа представляет собой единый веб-интерфейс, разделенный на 4 основные вкладки.

### 6.1. Создание виртуальных машин (Ubuntu, Windows, Свои образы)

Процесс создания ВМ автоматизирован через отправку JSON-манифеста в Kubernetes API. Вы можете выбрать один из трех типов системных дисков:

```
+-----------------------------------------------------------------------------------+
| 1. Пользователь отправляет форму: Имя="db-01", CPU=2, RAM=4GB, Disk=30GB          |
+-----------------------------------------------------------------------------------+
                                          |
                                          v
+-----------------------------------------------------------------------------------+
| 2. Бэкенд FastAPI генерирует случайный пароль (например, "xY89aB34zQ9p")          |
+-----------------------------------------------------------------------------------+
                                          |
                                          v
+-----------------------------------------------------------------------------------+
| 3. Бэкенд создает Secret "db-01-credentials" в K8s с логином "root" и паролем     |
+-----------------------------------------------------------------------------------+
                                          |
                                          v
+-----------------------------------------------------------------------------------+
| 4. Бэкенд генерирует YAML-манифест VirtualMachine и отправляет в KubeVirt API     |
+-----------------------------------------------------------------------------------+
                                          |
                                          v
+-----------------------------------------------------------------------------------+
| 5. CDI создает PVC диска "db-01-disk" и запускает импорт диска по HTTP/локально    |
+-----------------------------------------------------------------------------------+
                                          |
                                          v
+-----------------------------------------------------------------------------------+
| 6. После импорта запускается ВМ. Cloud-Init применяет логин "root" и пароль       |
+-----------------------------------------------------------------------------------+
```

* **Ubuntu Cloud:** Бэкенд создает DataVolume с источником скачивания официального облачного образа диска Ubuntu Server 24.04 LTS (Noble Numbat) в формате `.img`.
* **Windows ISO:** Бэкенд создает пустой жесткий диск (размером от 50 ГБ) для установки ОС, монтирует дисковод с установочным ISO образом Windows Server 2022 и подключает виртуальный привод с драйверами VirtIO.
* **Свой образ:** Бэкенд считывает список загруженных вами файлов в `/app/data/images`. Выбрав кастомный образ, CDI скачает его по локальной сети с адреса `http://127.0.0.1:8000/static/images/your-file.qcow2`.

#### Логин root по умолчанию
Для всех Linux-систем (Ubuntu и кастомных QCOW2 образов) бэкенд генерирует следующий Cloud-Init конфигурационный блок:
```yaml
#cloud-config
ssh_pwauth: True
disable_root: false
users:
  - name: root
    lock_passwd: false
    passwd: <сгенерированный_пароль>
runcmd:
  - apt-get update
  - apt-get install -y qemu-guest-agent
  - systemctl enable --now qemu-guest-agent
```
Cloud-init переопределяет стандартные политики безопасности, включает авторизацию по паролю по SSH для суперпользователя `root`, задает пароль и устанавливает `qemu-guest-agent` для точного получения IP-адресов внутри KubeVirt.

### 6.2. noVNC Экран и установка Windows Server

Ввиду отсутствия предустановленной графической оболочки и сетевых драйверов в стандартных ISO-образах Windows, процесс установки требует ручного вмешательства через веб-консоль.

#### Как запустить установку Windows Server:
1. Создайте ВМ с типом ОС **Windows ISO**.
2. Дождитесь, пока статус ВМ сменится на `Running` (это означает, что ISO загружен в локальный кэш и примонтирован к CD-ROM).
3. Нажмите кнопку **"Экран"** на карточке ВМ.
4. Откроется noVNC клиент. Вы увидите стандартный экран загрузки установщика Windows Server.
5. На этапе выбора жесткого диска для установки список дисков будет пуст. Это связано с тем, что KubeVirt использует производительные виртуальные шины `VirtIO`, которые не поддерживаются Windows по умолчанию.
6. Нажмите кнопку **"Load Driver"** (Загрузить драйвер) -> **Browse** (Обзор).
7. Разверните дерево дисков и найдите CD-дисковод с меткой **VirtIO-Drivers** (обычно диск `E:`).
8. Перейдите по пути: `viostor` -> `2k22` (или `w10` / `w11` в зависимости от версии ОС) -> `amd64`.
9. Нажмите **OK**. Установщик обнаружит драйвер **"Red Hat VirtIO SCSI controller"**. Нажмите **Next**. После загрузки драйвера в списке появится ваш жесткий диск размером 60 ГБ+.
10. Повторите процедуру для сетевой карты (опционально, если не определилась сеть автоматически): выберите драйвер в папке `NetKVM`.
11. Завершите установку Windows Server. Задайте пароль Администратора в окне VNC.

### 6.3. Динамическое изменение ресурсов и ресайз диска

Платформа поддерживает горячее и холодное изменение ресурсов.

#### CPU и RAM
Вы можете изменить количество ядер процессора и объем RAM в любой момент через настройки ВМ.
* Если ВМ запущена, новые параметры запишутся в спецификацию Kubernetes, но вступят в силу только после перезапуска виртуалки (выполняется нажатием кнопки "Рестарт" в панели).
* На бэкенде это реализовано через JSON Patch запрос к CustomObject:
  ```python
  body = [
      {"op": "replace", "path": "/spec/template/spec/domain/cpu/cores", "value": cpu_cores},
      {"op": "replace", "path": "/spec/template/spec/domain/resources/requests/memory", "value": f"{memory_gb}Gi"}
  ]
  ```

#### Расширение жесткого диска (HDD)
Благодаря использованию K3s local-path провайдера, поддерживающего динамическое расширение томов (`allowVolumeExpansion: true`), вы можете увеличить размер диска "на лету".
* **Увеличение размера:** Бэкенд находит PVC, привязанный к вашей ВМ, и обновляет размер хранилища в его спецификации:
  ```python
  body = {"spec": {"resources": {"requests": {"storage": f"{new_size_gb}Gi"}}}}
  core_api.patch_namespaced_persistent_volume_claim(pvc_name, namespace, body)
  ```
* **Ограничение на уменьшение:** Интерфейс панели блокирует уменьшение диска. Ползунок выбора размера жесткого диска автоматически начинается с текущего объема диска ВМ. Это связано с тем, что уменьшение размера файловых систем (особенно XFS/Ext4) на смонтированных томах невозможно без потери данных и не поддерживается Kubernetes API.

### 6.4. Резервные копии и восстановление дисков

Резервное копирование реализовано на уровне хранилища Kubernetes посредством клонирования томов (PVC Cloning). Данный подход гарантирует 100% совместимость со всеми типами файловых систем и не зависит от дистрибутива ОС.

```
+----------------------------------------------------------------------------------------+
|                                    СОЗДАНИЕ БЭКАПА                                     |
|                                                                                        |
|   +-----------------------+      Клонирование PVC      +---------------------------+   |
|   |  Системный диск ВМ    | =========================> |  Резервная копия (PVC)    |   |
|   |  (myvm-disk, 20GB)    |    (CDI импортер подов)    |  (myvm-backup-1718223, 20G|   |
|   +-----------------------+                            +---------------------------+   |
+----------------------------------------------------------------------------------------+

+----------------------------------------------------------------------------------------+
|                                  ВОССТАНОВЛЕНИЕ ВМ                                     |
|                                                                                        |
|   +-----------------------+       Удаление диска       +---------------------------+   |
|   |  Системный диск ВМ    | -------------------------> |        (Удалено)          |   |
|   |  (myvm-disk, 20GB)    |                            |                           |   |
|   +-----------------------+                            +---------------------------+   |
|                                                              |                         |
|                                                              v                         |
|   +-----------------------+      Клонирование бэкапа   +---------------------------+   |
|   |  Новый системный диск | <========================= |  Резервная копия (PVC)    |   |
|   |  (myvm-disk, 20GB)    |                            |  (myvm-backup-1718223, 20G|   |
|   +-----------------------+                            +---------------------------+   |
+----------------------------------------------------------------------------------------+
```

#### Создание бэкапа:
1. При нажатии кнопки "Создать копию" бэкенд находит оригинальный PVC ВМ и считывает его точный размер.
2. Создается манифест `DataVolume` с меткой источника `pvc`, указывающей на системный диск виртуалки:
   ```json
   "spec": {
     "source": {
       "pvc": {
         "name": "original-pvc-name",
         "namespace": "default"
       }
     }
   }
   ```
3. Kubernetes создает новый PVC `{vm_name}-backup-{timestamp}` и запускает под-клонировщик CDI.
4. Прогресс копирования в реальном времени отображается на фронтенде (считывается статус `.status.progress` из DataVolume).

#### Восстановление диска:
Восстановление диска заменяет системный накопитель ВМ на сохраненную копию.
1. Бэкенд проверяет состояние ВМ. Если она работает, бэкенд шлет сигнал на выключение ВМ (`VirtualMachine.spec.running = false`) и дожидается остановки.
2. Старый PVC диска удаляется из Kubernetes.
3. Создается новый `DataVolume` с оригинальным именем диска ВМ (например, `test-vm-disk`), но источником данных (`source.pvc`) выступает выбранный бэкап PVC (например, `test-vm-backup-1718223`).
4. После завершения клонирования ВМ готова к работе и запускается с сохраненной контрольной точки.

### 6.5. Кастомные образы ОС и хранилище

Вкладка **"Образы дисков"** позволяет загружать собственные дистрибутивы систем.

* **Хранение на хосте:** Загруженные файлы сохраняются в папку `./data/images/` в корне проекта на хост-машине.
* **Потоковая загрузка:** Бэкенд считывает поток байт через `shutil.copyfileobj` чанками и записывает их на диск. Это предотвращает переполнение оперативной памяти бэкенда (RAM не превышает 50–100 МБ даже при загрузке ISO файла размером 5 ГБ).
* **Прогресс-бар:** Фронтенд использует XMLHttpRequest `onprogress` для вычисления процента переданных данных и отрисовки анимации.
* **Интеграция с CDI:** Бэкенд раздает папку `./data/images/` как статические файлы по адресу `/static/images/`. Когда вы создаете виртуалку из своего образа, CDI-контроллер скачивает образ по этому URL:
  `http://127.0.0.1:8000/static/images/your-uploaded-image.qcow2`

### 6.6. Внешний SSH мониторинг серверов

Вы можете подключить любой внешний сервер на базе Linux (Ubuntu, Debian, CentOS, AlmaLinux, Fedora) по его IP и SSH паролю. Мониторинг является **безагентным (Agentless)** — удаленный сервер не требует установки тяжелых программ мониторинга.

#### Как это работает:
1. Вы вводите IP-адрес, SSH порт (обычно 22), логин (например, `root`) и пароль.
2. Бэкенд проверяет возможность авторизации по SSH с таймаутом в 5 секунд.
3. Реквизиты сохраняются в зашифрованном JSON файле `/app/data/external_servers.json` на сервере.
4. При открытии дашборда бэкенд раз в 6 секунд открывает SSH-сессию и последовательно выполняет команды диагностики:

#### Команды сбора метрик:
* **Распределение ядер CPU:** `nproc` (возвращает количество ядер).
* **Текущая загрузка CPU (%):**
  ```bash
  vmstat 1 2 | tail -n 1 | awk '{print 100 - $15}'
  ```
  *Команда собирает статистику системных тиков за 1 секунду. 15-я колонка в выводе vmstat — это процент времени простоя процессора (idle). Вычитая его из 100, мы получаем точную мгновенную нагрузку на CPU.*
* **Память RAM:**
  ```bash
  free -m
  ```
  *Бэкенд парсит вторую строчку вывода (`Mem:`) для определения общего, занятого и свободного объема памяти в мегабайтах.*
* **Дисковый накопитель:**
  ```bash
  df -m / | tail -n 1
  ```
  *Возвращает размер диска, занятое пространство в мегабайтах и процент утилизации корневого раздела.*
* **Топ-10 процессов:**
  ```bash
  ps aux --sort=-%cpu | head -n 11
  ```
  *Парсится в массив объектов с полями PID, USER, %CPU, %MEM и COMMAND для вывода в интерактивную таблицу.*
* **Службы Systemd:**
  ```bash
  systemctl list-units --type=service --state=running --no-legend | head -n 15
  ```
  *Считывает первые 15 запущенных системных служб Linux для контроля работы веб-серверов, баз данных и демонов.*
* **Контейнеры Docker:**
  Сначала проверяется наличие docker в системе (`which docker`). Если docker доступен, выполняется команда:
  ```bash
  docker ps --format "{{.ID}}\t{{.Names}}\t{{.Status}}\t{{.Image}}"
  ```
  *Вывод парсится с разделителем-табуляцией для отображения запущенных контейнеров во вкладке мониторинга.*

### 6.7. Админка Docker на хосте

Панель имеет встроенный модуль администрирования контейнеров, запущенных на самом физическом сервере (гипервизоре).

* **Доступ к сокету:** Контейнер бэкенда примонтирован к хостовому сокету `/var/run/docker.sock:/var/run/docker.sock:rw`. Это дает бэкенду полные права на управление Docker демоном хоста.
* **Управление:** Вкладка опрашивает Docker API хоста и выводит таблицу контейнеров. Кнопки Старт/Стоп/Рестарт отправляют команды `container.start()`, `container.stop(timeout=10)` и `container.restart(timeout=10)` через Python SDK `docker`.
* Это позволяет администратору перезапускать саму панель управления, просматривать порты и контролировать системные сервисы хоста напрямую из браузера.

## 7. Справочник API Эндпоинтов (REST & WebSockets)

Вы можете интегрировать панель с внешними скриптами автоматизации или биллингом. Все эндпоинты возвращают стандартный JSON.

### 7.1. Управление локальными ВМ (`/api/vms`)

* **`GET /api/vms`**
  * *Описание:* Получить список всех ВМ и запущенных инстансов.
  * *Ответ:* Массив объектов VM.
* **`POST /api/vms`**
  * *Описание:* Создать новую ВМ.
  * *Тело запроса (JSON):*
    ```json
    {
      "name": "vm-test",
      "os_type": "ubuntu",
      "cpu_cores": 2,
      "memory_gb": 4,
      "disk_gb": 30
    }
    ```
* **`DELETE /api/vms/{name}`**
  * *Описание:* Удалить ВМ, связанные диски и секреты авторизации.
* **`POST /api/vms/{name}/start`**
  * *Описание:* Включить ВМ.
* **`POST /api/vms/{name}/stop`**
  * *Описание:* Выключить ВМ.
* **`POST /api/vms/{name}/restart`**
  * *Описание:* Перезагрузить ВМ.
* **`GET /api/vms/{name}/metrics`**
  * *Описание:* Получить текущее использование CPU и RAM контейнера ВМ.
* **`POST /api/vms/{name}/resize`**
  * *Описание:* Изменить ресурсы и размер диска.
  * *Тело запроса (JSON):* `{"cpu_cores": 4, "memory_gb": 8, "disk_gb": 50}`
* **`POST /api/vms/{name}/backup`**
  * *Описание:* Запустить создание резервной копии диска.
* **`GET /api/vms/{name}/backups`**
  * *Описание:* Список бэкапов ВМ.
* **`POST /api/vms/{name}/restore/{backup_name}`**
  * *Описание:* Восстановить диск ВМ из выбранной копии.

### 7.2. В VNC соединение (WebSockets)
* **`WS /api/vnc/{name}`**
  * *Описание:* Устанавливает WebSocket-соединение для проксирования VNC-экрана. Передает бинарные RFB-сообщения.

### 7.3. Загрузка образов (`/api/images`)
* **`GET /api/images`** — Список загруженных ISO/QCOW2 образов.
* **`POST /api/images/upload`** — Загрузить файл образа (Multipart Form Data).
* **`DELETE /api/images/{filename}`** — Удалить файл образа с диска.

### 7.4. Внешние серверы (`/api/external-servers`)
* **`GET /api/external-servers`** — Список серверов и их онлайн-статусы.
* **`POST /api/external-servers`** — Подключить новый сервер (с тестом SSH).
* **`DELETE /api/external-servers/{id}`** — Удалить сервер.
* **`GET /api/external-servers/{id}/details`** — Получить живые метрики по SSH.

## 8. Решение возможных проблем (Troubleshooting)

### ВМ зависла в статусе `Importing` или `PvcBound`
1. **Причина:** CDI-контроллер не может скачать образ диска по указанной ссылке (таймаут сети или битая ссылка).
2. **Как проверить:** 
   ```bash
   kubectl get pods -n default
   ```
   Найдите под с именем `importer-<vm-name>-disk-*`. Посмотрите его логи:
   ```bash
   kubectl logs importer-<vm-name>-disk-xxxxx -n default
   ```
3. **Решение:** Проверьте доступность интернета на хосте или корректность загруженного образа во вкладке "Образы дисков".

### Ошибка `401 Unauthorized` при попытке открыть Экран (VNC)
1. **Причина:** Бэкенд не смог авторизоваться в API-сервере Kubernetes при создании WebSocket-туннеля.
2. **Решение:** Убедитесь, что файл `kubeconfig` примонтирован в контейнер бэкенда (`/root/.kube/config`). Если в `kubeconfig` используются пути к файлам сертификатов (client-certificate/client-key), они также должны быть доступны внутри контейнера, либо сертификаты должны быть встроены в сам файл `config` в формате `base64` (параметры `client-certificate-data` и `client-key-data` — K3s по умолчанию делает именно так).

### Внешний сервер постоянно висит в статусе `Offline`
1. **Причина:** Неверные реквизиты авторизации или брандмауэр блокирует порт SSH (22).
2. **Как проверить:** Попробуйте подключиться к серверу по SSH вручную из консоли вашей Ubuntu-ноды:
   ```bash
   ssh root@<IP_внешнего_сервера> -p 22
   ```
3. **Решение:** Добавьте IP вашей ноды в белый список брандмауэра (`ufw` / `iptables`) удаленного сервера и убедитесь, что в конфигурации SSH удаленного сервера (`/etc/ssh/sshd_config`) разрешен вход по паролю: `PasswordAuthentication yes`.
