# ByteBurners Hosting

Панель для собственного хостинга виртуальных машин, приложений, баз данных и файлов. ВМ запускаются через KubeVirt/QEMU/KVM в K3s; веб-интерфейс объединяет управление ресурсами, доступом, дополнительными дисками, S3-копиями и мониторингом.

Основной сценарий — установка на отдельный Linux-сервер и управление инфраструктурой из браузера. Репозиторий также содержит инструменты для многоузлового развёртывания, CLI и Terraform-провайдер. Внутреннее имя **Aegis / Antigravity** сохраняется в названиях контейнеров, переменных и API.

README описывает текущую реализацию, а не планируемые возможности. Проект устанавливается из исходников с локальной сборкой Docker-образов; готового закрытого однофайлового установщика и системы лицензирования пока нет.

## Архитектура

| Компонент | Назначение |
|---|---|
| React + Vite | Пользовательская панель; статическая сборка отдаётся Nginx |
| FastAPI | REST API, авторизация, проверки прав и квот, интеграции с Kubernetes, Docker и SSH |
| Python worker + Pika | Потребитель очереди RabbitMQ и фоновые потоки; Celery не используется |
| PostgreSQL | Метаданные панели: пользователи, ресурсы, настройки, задания, архивы и расписания |
| RabbitMQ | Очередь задач `vm_tasks` |
| K3s + KubeVirt | Запуск и управление виртуальными машинами |
| CDI + KubeVirt Export API | Импорт образов и экспорт постоянных дисков для S3-копирования |
| Multus, bridge CNI, dnsmasq | Дополнительные сети ВМ и мост `br-vms` |
| OpenEBS LVM | Локальные блочные PVC и LVM-пул сетевых дисков |
| MinIO | S3 API, пользовательские объекты и резервные копии |
| Prometheus | Метрики хоста и ВМ |
| Хостовый Nginx + iptables | Балансировка и TCP-проброс портов к ВМ |
| Caddy | Доменные HTTP/HTTPS-прокси и сертификаты |
| Go `aegis-orchestrator` | Дополнительный HCI/API-компонент, подключённый к системной БД |
| Docker Mailserver + Roundcube | Почтовые ящики и веб-почта |

Создание ВМ проходит через API → PostgreSQL → RabbitMQ → worker → Kubernetes. Часть операций выполняется непосредственно в API, а S3-операции обрабатываются фоновым потоком worker по сохранённому в PostgreSQL состоянию.

Основные сервисы поднимаются из [docker-compose.yml](docker-compose.yml). Контейнеры `aegis-caddy` и `aegis-registry` создаются отдельно через Docker API по необходимости.

Backend и worker работают с сетью/PID хоста, Docker-сокетом и kubeconfig. Для управления сетью и LVM используются `nsenter`, capabilities и разрешения на устройства. Это административная панель с существенными привилегиями на сервере, а не изолированное обычное веб-приложение.

## Требования

Установщик рассчитан на чистую **Ubuntu Server 22.04 / 24.04** с systemd и правами root.

Для основной конфигурации нужны:

- x86_64/amd64: каталог стандартных гостевых образов ориентирован на эту архитектуру;
- аппаратная виртуализация и доступный `/dev/kvm`;
- интернет для пакетов, Kubernetes-компонентов, Docker-образов, исходников MinIO/Caddy и гостевых образов;
- свободное место под системные и дополнительные диски, импорты CDI, S3-архивы и слои Docker;
- CPU и RAM с запасом для K3s, сервисов панели и выбранных ВМ;
- стабильная сеть и доступ администратора к самому серверу.

Фиксированного гарантированного минимума для всего стека нет: количество и размеры ВМ, объём копий и включённые сервисы определяют реальные требования. Не отдавайте гостям всю память и всё место хоста — сервисам панели и временным импортам тоже нужны ресурсы.

Если хост сам является ВМ, включите nested virtualization во внешнем гипервизоре. Для Proxmox, который будет запускать свои ВМ, вложенная виртуализация нужна также внутри гостя. Режим программной эмуляции предусмотрен установщиком, но не заменяет KVM для нормальной производительности.

Проверки до установки:

~~~bash
uname -m
ls -l /dev/kvm
lscpu
free -h
df -h / /var/lib
ip route
~~~

Не запускайте установщик на сервере с важной действующей инфраструктурой без резервной копии: он меняет пакеты, сеть, systemd, Nginx, Kubernetes и настройки хранения.

## Установка

### Новый сервер

Команды установки выполняйте в root-сессии сервера (при необходимости сначала `sudo -i`):

~~~bash
sudo apt-get update
sudo apt-get install -y git
sudo git clone https://github.com/Monopoly450/Hosting.git /root/Hosting
cd /root/Hosting
sudo bash install.sh
~~~

Мастер спрашивает пароли и параметры установки. Пустое значение для секретов позволяет сгенерировать случайный пароль. Затем он создаёт `.env`, устанавливает Docker/Compose, K3s, Multus, KubeVirt, CDI и Prometheus, настраивает мост, OpenEBS LVM, Fail2Ban и автозапуск, собирает и запускает контейнеры.

Неинтерактивный запуск:

~~~bash
sudo bash install.sh --yes
~~~

В режиме `--yes` существующий `.env` сохраняется; при его отсутствии настройки и секреты создаются автоматически. Повторный запуск установщика не равнозначен чистой переустановке и не предназначен для удаления старых данных.

Если репозиторий уже находится на сервере, новый `git clone` не нужен: перейдите в его каталог и запустите `install.sh`. Интернет для остальных зависимостей всё равно требуется.

### Важный выбор хранилища

Для схемы **«системные диски и БД на local-path, LVM только для сетевых дисков»** выберите в мастере:

~~~dotenv
STORAGE_CLASS=local-path
NETWORK_STORAGE_CLASS=openebs-lvm
~~~

В текущем `install.sh` мастер предлагает `openebs-lvm` для `STORAGE_CLASS`, тогда как [.env.example](.env.example) содержит `local-path`. Поэтому не полагайтесь на значение по умолчанию: выбирайте класс системных дисков явно. Если `NETWORK_STORAGE_CLASS` отсутствует в `.env`, backend использует `openebs-lvm`.

Новые S3-снимки и бэкапы работают и с `local-path`: им не требуется CSI VolumeSnapshotClass.

### Первый вход

Прямой адрес панели:

~~~text
https://<IP-сервера>:8443
~~~

Порт `8080` перенаправляет на `8443`. При прямом доступе используется локальный самоподписанный сертификат; для доверенного HTTPS настройте домен.

При первом создании системной БД:

- логин — `admin`;
- начальный пароль — значение `ADMIN_TOKEN`, выбранное или сгенерированное установщиком.

Установщик выводит начальные реквизиты; они также находятся в `.env`. После первого входа задайте отдельный пароль пользователя и настройте 2FA. Изменение `ADMIN_TOKEN` в файле не меняет автоматически пароль уже существующего пользователя `admin`.

Проверьте запуск:

~~~bash
docker compose ps
kubectl get nodes
kubectl get pods -A
curl -fsS http://127.0.0.1:8000/
~~~

### Несколько физических нод

В репозитории есть отдельные bootstrap-скрипты:

- [bootstrap-cluster-storage.sh](scripts/bootstrap-cluster-storage.sh) — NFS-сервер хранения;
- [bootstrap-cluster-node1.sh](scripts/bootstrap-cluster-node1.sh) — первая нода;
- [bootstrap-cluster-node2.sh](scripts/bootstrap-cluster-node2.sh) — дополнительная нода;
- [node-fencer.py](scripts/node-fencer.py) — инструмент fencing.

Это отдельная инфраструктурная схема, не кнопка «Кластеры» в панели. Для неё нужны общая СХД, корректная сеть и проверка сценариев отказа. Одноузловый K3s, local-path или локальный OpenEBS LVM сами по себе не обеспечивают HA и перенос локальных дисков между хостами.

Скрипты хранения могут инициализировать устройства и менять LVM. Перед запуском прочитайте их и сохраните данные; не передавайте диск с существующими данными как свободное устройство.

## Создание и управление ВМ

### Операционные системы

| Тип | Как разворачивается | Особенности доступа |
|---|---|---|
| Ubuntu, Debian | Cloud image + cloud-init | VNC, SSH; парольный веб-терминал либо инструкции по своему ключу |
| CentOS Stream, AlmaLinux, Rocky Linux, Fedora | Cloud image + cloud-init | Пакеты и окружения зависят от семейства ОС |
| openSUSE, Arch Linux, Alpine Linux | Cloud image + cloud-init | Учитываются различия менеджеров пакетов и системы инициализации |
| BitrixVM | Linux-образ с настройкой Bitrix-окружения | Отдельный веб-стек; несовместимые окружения блокируются |
| Windows Server | ISO, ручная установка через VNC | VirtIO-драйверы и RDP; веб-терминал, бэкапы и снимки отключены |
| Proxmox VE | ISO, ручная установка через VNC | HTTPS на внутреннем 8006; веб-терминал панели отключён |
| TrueNAS SCALE | ISO, ручная установка через VNC | Дальнейшая настройка в TrueNAS; веб-терминал панели отключён |
| Свой образ | Загруженный ISO/QCOW2/IMG/RAW | Поведение зависит от содержимого образа, сети и гостевой ОС |

Версии и URL образов перечислены в форме создания и коде каталога. Они не гарантируют доступность загрузки у производителя; можно использовать собственный образ через менеджер образов.

### Поля создания Linux-ВМ

Указываются имя, ОС/образ, CPU, RAM и начальный размер системного диска. Дополнительно доступны:

- пакеты через запятую, например `htop, curl, jq`;
- сетевые ресурсы NFS/PVC;
- публичный SSH-ключ;
- пользовательский YAML Cloud-Init.

Для Windows, Proxmox и TrueNAS поля cloud-init, пакетов, NFS/PVC и SSH-ключа скрыты. Черновик Linux-настроек не отправляется при переключении на ISO-ОС. Готовые окружения выбираются в «Маркетплейсе», а обычная форма создаёт базовую ОС.

Пример пользовательского Cloud-Init:

~~~yaml
#cloud-config
timezone: Asia/Yekaterinburg
write_files:
  - path: /var/tmp/hosting-test.txt
    permissions: '0644'
    content: |
      Проверка пользовательского Cloud-Init.
runcmd:
  - [sh, -c, 'touch /var/tmp/hosting-runcmd-ok']
~~~

Cloud-Init дополняет базовую конфигурацию панели. Проверяются формат, структура YAML, публичные ключи и совместимость полей; shell-скрипт или MIME вместо `#cloud-config` в этом поле не поддерживается. Комментарии и содержимое файлов могут быть на русском, имена ВМ/PVC, пакетов и ключей YAML — латиницей.

Успешная проверка формы не гарантирует, что пакет существует в репозитории ОС или команда выполнится. Эти ошибки проверяются внутри гостя:

~~~bash
sudo cloud-init status --wait --long
sudo tail -n 100 /var/log/cloud-init-output.log
~~~

Cloud-Init применяется при первом запуске новой ВМ. Изменение исходного YAML в панели не является командой повторного запуска cloud-init на уже созданной машине.

Полный сценарий проверки всех полей и ошибочного ввода: [docs/VM_CREATION_TEST.md](docs/VM_CREATION_TEST.md).

### Ресурсы и состояние ВМ

В деталях доступны запуск, остановка, перезагрузка, VNC, метрики, клонирование и настройки. Возможность действий зависит от роли, ОС и текущих операций.

CPU и RAM сохраняются кнопкой «Сохранить настройки ресурсов». Чтобы новые значения применились к уже запущенной ВМ, выполните Stop, дождитесь остановки, затем Start. Перезагрузка только внутри гостевой ОС не пересоздаёт VMI.

Системный диск в настройках показывается для просмотра. Для дополнительного места создайте и подключите отдельный сетевой диск. Ползунков ограничения IOPS/MB/s больше нет; worker снимает ранее сохранённые ограничения. API расширения системного диска оставлен для совместимости, но это не основной сценарий интерфейса.

Подробнее: [docs/VM_RESOURCES.md](docs/VM_RESOURCES.md).

## Подключение и проброс портов

### Стабильные внешние порты

Стандартные правила вычисляются от **ID ВМ в системной БД**, а не от текущего IP:

| Назначение | Внешний TCP-порт | Внутренний порт |
|---|---|---|
| SSH | `22000 + ID` | 22 |
| HTTP обычной Linux-ВМ | `28000 + ID` | 80 |
| HTTPS обычной Linux-ВМ | `44300 + ID` | 443 |
| RDP Windows | `33000 + ID` | 3389 |
| Панель Proxmox | `28000 + ID` | 8006, HTTPS |
| Сервис поддерживаемого шаблона на отдельном порту | `29000 + ID` | Порт сервиса, например Grafana 3000 или Portainer 9000 |

Это таблица назначения портов, не обещание открыть все перечисленные правила для каждой ОС. Windows по умолчанию получает RDP, SSH и HTTP; Proxmox — SSH и HTTPS-панель на 8006. Маркетплейс и деплой могут задавать собственные правила.

Настройки позволяют изменять пробросы и белые списки IP. Один внешний порт нельзя использовать в двух правилах одной ВМ. Проверяйте также конфликты с другими ВМ и службами хоста.

Worker сверяет DNAT-правила и восстанавливает их при смене IP или исчезновении правил. Открытый проброс не запускает сервис внутри ВМ и не открывает порт на домашнем роутере или у провайдера.

### SSH с собственным ключом

На компьютере, с которого будете подключаться, создайте ключ с отдельным именем. Если файл уже существует, не соглашайтесь на его перезапись:

~~~bash
ssh-keygen -t ed25519 -f ~/.ssh/hosting_ed25519 -C hosting
cat ~/.ssh/hosting_ed25519.pub
~~~

В форму создания вставляется содержимое **публичного** файла `.pub`. Приватный файл `hosting_ed25519` остаётся на вашем компьютере. Используйте парольную фразу для его защиты.

Если задан свой ключ, парольная SSH-аутентификация отключается, а вкладка «Терминал / SSH» показывает инструкции вместо парольного веб-терминала. VNC остаётся доступен. Панель принимает путь к приватному файлу для формирования команды, но не получает его содержимое.

Пример для Linux-ВМ с ID 8 и пользователем `ubuntu`:

~~~bash
ssh -i ~/.ssh/hosting_ed25519 -o IdentitiesOnly=yes -o PreferredAuthentications=publickey -p 22008 ubuntu@panel.example.com
~~~

С хоста hosting можно подключаться по маршрутизируемому IP самой ВМ:

~~~bash
ssh -i /путь/к/приватному/ключу -o IdentitiesOnly=yes 'ubuntu@<IP-ВМ>'
~~~

Файл ключа не нужно запускать как программу. Путь после `-i` должен существовать на компьютере, где выполняется SSH, и соответствовать публичному ключу этой ВМ. Ключ, созданный только на hosting, не появится автоматически на Mac.

Пользователь зависит от ОС и образа; копируйте имя из реквизитов ВМ. Пользовательские изменения `users`, паролей или SSH-настроек в Cloud-Init могут сделать сгенерированные панелью реквизиты неприменимыми.

### Proxmox

Панель Proxmox использует **HTTPS на 8006 внутри гостя**. Проброс создаётся автоматически. Для ВМ с ID 10:

~~~text
https://panel.example.com:28010
~~~

Старое стандартное правило `28010 → 80` для Proxmox автоматически трактуется как `28010 → 8006`, если отдельного TCP-проброса на 8006 ещё нет. Пользовательские правила не заменяются; белый список старого правила сохраняется. В карточке показываются ссылка и проверка доступности 8006 внутри ВМ.

Сначала завершите установку через VNC и загрузитесь с установленного диска. Для входа в Proxmox используйте `root`, область `Linux PAM` и пароль, заданный в установщике, а не сгенерированный пароль панели hosting.

Статус «Запущена» означает работу виртуальной машины. Он не подтверждает завершение ISO-установки, правильность сети или запуск `pveproxy`.

### Windows и TrueNAS

Windows устанавливается через VNC. Для дискового/сетевого оборудования нужны VirtIO-драйверы с подключённого диска. RDP необходимо разрешить в самой Windows, настроить гостевой фаервол и использовать учётные данные, заданные в установщике.

TrueNAS устанавливается и настраивается через VNC и собственный веб-интерфейс. Linux cloud-init к ISO TrueNAS не применяется. Для внешнего доступа создайте проброс на фактический HTTP/HTTPS-порт, выбранный в настройках TrueNAS.

## Хранилища и сетевые диски

### Три разных назначения

| Данные | Где хранятся | Настройка |
|---|---|---|
| Системные диски ВМ и PVC приватных БД | Kubernetes PVC выбранного класса | `STORAGE_CLASS` |
| Новые дополнительные сетевые диски | OpenEBS LVM, PVC в режиме Block, группа `vg-aegis` | `NETWORK_STORAGE_CLASS` |
| Новые бэкапы, снимки и SQL-дампы | MinIO, приватный бакет владельца | S3-учётные данные сервисов |

Смена StorageClass влияет на новые ресурсы. Существующие PVC не переезжают автоматически.

### LVM-пул

Скрипт [install-openebs-lvm.sh](scripts/install-openebs-lvm.sh) настраивает OpenEBS LVM и thin provisioning. В типовой локальной схеме используются:

- группа `vg-aegis`;
- класс `openebs-lvm`;
- файл-образ `/var/lib/aegis/lvm-storage.img` и loop-устройство;
- службы восстановления loop/LVM после загрузки и мониторинга thin-pool.

Размер пула выбирается при установке. Разреженный файл не создаёт дополнительного физического места: он занимает backing filesystem по мере записи. Нужно следить и за LVM, и за свободным местом реального раздела.

Карточка «Сетевые диски (LVM)» показывает физические показатели пула и отдельную строку выделения только сетевым дискам. Она не прибавляет VM-бэкапы, БД и системные диски в строку «Выделено сетевым дискам». Но если `STORAGE_CLASS` также направлен в этот LVM-пул, физическое использование других ресурсов влияет на его свободное место.

Отсутствующий LVM-класс или нехватка места приводят к отказу создания сетевого диска; автоматического fallback на `local-path` для новых сетевых дисков нет.

### Подключение PVC и NFS

Сетевой диск можно подключить отдельно либо указать при создании Linux-ВМ. Для PVC используйте полное имя, например `vol-1-test`, а не только отображаемое короткое имя `test`.

В списке дисков отображаются:

- «Свободен» — нет связи с ВМ;
- «Подключается» — диск зарезервирован при создании ВМ;
- «Подключён» — найдена фактическая связь с VM/VMI;
- имя ВМ и тип связи, в том числе «Подключён при создании ВМ».

Занятый или зарезервированный диск нельзя повторно подключить или удалить. Диск, включённый в конфигурацию при создании без hotplug, нельзя отсоединить кнопкой горячего отключения.

**Подключение не означает форматирование или монтирование.** PVC появляется внутри гостя отдельным диском. Настройте файловую систему и точку монтирования самостоятельно; не форматируйте диски с существующими данными.

Проверка внутри Linux-гостя:

~~~bash
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
findmnt
~~~

Для NFS формат поля — `192.168.1.10:/shared`. Ресурс монтируется в `/mnt/network_drive_0`, `_1` и далее по индексу записи. Панель проверяет формат адреса, но доступность экспорта, права и сеть нужно обеспечить отдельно.

## Бэкапы и снимки

### Личный S3-бакет владельца

Новые ручные и плановые копии ВМ, снимки и SQL-дампы сохраняются в бакете:

~~~text
aegis-backups-u<ID-владельца>
~~~

Бакет создаётся при первом копировании. Когда администратор делает копию чужой ВМ, используется бакет владельца ВМ, а не администратора. Служебный бакет виден в разделе S3 и не расходует лимит обычных пользовательских бакетов.

Пользовательские ключи служебного бакета предназначены для чтения. Загрузка, удаление объектов и удаление бакета через S3-панель запрещены; удалять копии следует через соответствующие вкладки ВМ/БД. Корневой администратор MinIO сохраняет полный доступ.

### Что такое снимок в текущей версии

«Снимок» — **полная дисковая точка восстановления в S3**, а не быстрый LVM/CSI-снимок и не сохранение оперативной памяти.

Копируются постоянные диски ВМ, включая подключённые дополнительные диски. Сохраняется манифест с описанием ВМ и PVC. ISO/CD-ROM, containerDisk, cloud-init и содержимое внешних Secret/ConfigMap отдельно не экспортируются.

ВМ выключается на время выгрузки; после завершения или обработки ошибки восстанавливается исходное состояние питания. Поэтому создание такой копии вызывает простой.

Копия отмечается готовой только после завершения выгрузки. Копию со статусом «Не удался» нельзя использовать для отката. Windows исключён из новых бэкапов, снимков и расписаний.

### Восстановление и удаление

При откате:

1. Проверяется принадлежность копии, идентичность исходной ВМ, состав дисков и S3-объекты.
2. Диски импортируются в новые CDI DataVolume/PVC.
3. После готовности всех импортов выполняется переключение дисков.
4. Финализация возвращает исходное состояние питания.

Текущие CPU/RAM и сеть сохраняются; это не полное восстановление всех настроек панели из прошлого состояния. При изменившемся составе дисков автоматический откат может быть запрещён. Для временных импортных дисков требуется дополнительное свободное место.

Не удаляйте исходные PVC и не снимайте блокировки операций вручную. Удаление архива через панель удаляет объекты его префикса в S3 и запись архива, но не должно удалять действующий диск ВМ.

Показатели занятого места на дашборде могут обновляться с задержкой из-за опроса и кэша. Проверяйте результат операции и фактические объекты/PVC, а не только карточку ёмкости.

### Расписания и требования

Расписания поддерживают hourly/daily/weekly, число сохраняемых копий и ручной запуск. Часы расписаний в backend — **UTC**. Ротация удаляет старые копии по retention; заранее учитывайте их объём и время простоя.

Для ВМ нужны MinIO, CDI и KubeVirt Export API с feature gate `VMExport`. На новых установках gate включается установщиком; для обновлённого старого кластера:

~~~bash
sudo bash scripts/enable-vm-export.sh
~~~

Импортирующие Kubernetes-поды должны иметь доступ к MinIO по адресу хоста и TCP 9000. Полные raw-образы могут занимать больше места, чем реально используемые данные внутри гостя.

Старые локальные копии и CSI-снимки сохраняют отдельные пути совместимости; обновление не переносит их автоматически в S3.

Подробнее о формате, восстановлении и типовых ошибках: [docs/S3_BACKUPS.md](docs/S3_BACKUPS.md).

## Приложения и дополнительные сервисы

### Маркетплейс и деплой

Маркетплейс содержит два типа развёртывания:

- Docker Compose-приложения, например WordPress, Ghost, Nextcloud, n8n, Uptime Kuma, Vaultwarden, PostgreSQL и Redis;
- системные окружения: LAMP, LEMP, Docker, Portainer, Grafana, Node.js, Python, PostgreSQL, Redis, WordPress и Zabbix.

Под каждое развёртывание создаётся ВМ. Для окружений учитывается совместимость с выбранной ОС; неподдерживаемые сочетания отклоняются. Установка идёт через cloud-init и может занимать заметно больше времени, чем запуск VMI.

Деплой из Git использует HTTPS URL и выбранную ветку. Приложение запускается внутри выделенной ВМ, а не автоматически как Kubernetes Deployment. Тип запуска — Compose, Dockerfile, Node.js, Python, статический сайт или своя команда.

Ссылка на приложение не гарантирует готовность. Проверяйте cloud-init, контейнеры/службы в госте и внутренний порт приложения.

### Приватные базы данных

PostgreSQL и MySQL разворачиваются в отдельных Kubernetes-подах с PVC. Привязка к ВМ управляет доступом через сетевую политику.

В карточке БД находятся реквизиты, примеры для клиента/кода, мониторинг, SQL-консоль и S3-дампы. Используйте фактический host/port из панели; служебные `aegis-db` и `aegis-mariadb` не являются пользовательскими БД.

Восстановление SQL-копии заменяет содержимое базы: изменённые записи возвращаются к состоянию дампа, а таблицы и другие пользовательские объекты, созданные после копии, удаляются. На это время остановите приложения, записывающие в БД. Завершённые старые SQL-дампы поддерживаются; пустые, обрезанные и дампы другой СУБД отклоняются до изменения данных. Объекты, не включённые в старый дамп, из него восстановить нельзя.

Для PostgreSQL очистка и импорт выполняются в одной транзакции с остановкой при SQL-ошибке: неудачная операция не фиксирует изменения. Для MySQL/MariaDB перед заменой сохраняется страховочный дамп в поде; при ошибке выполняется попытка возврата прежней базы. Если возврат тоже не удался, операция сообщает об ошибке и сохраняет путь к страховочной копии — не перезапускайте/удаляйте под до её извлечения. MySQL DDL не является транзакционным, поэтому это не гарантия атомарного отката при сбое хоста или вмешательстве других клиентов.

Во время копирования/восстановления повторные операции для той же БД блокируются. При таймауте или разрыве связи не запускайте восстановление повторно, пока не проверите процесс в поде. После успешного отката список таблиц и метрики обновляются, а прежний результат SQL-консоли очищается: повторно выполните нужный `SELECT`.

Запрос `CREATE TABLE` не возвращает набор строк, а строки, начинающиеся с `--`, являются комментариями. Для проверки результатов выполните, например, `SELECT 1;`.

### S3 и контейнерный реестр

Обычные бакеты создаются с отдельными ключами и политиками. S3 API доступен на TCP 9000. `STORAGE_DOMAIN` открывает веб-консоль MinIO, а не заменяет endpoint S3 API. По умолчанию порт 9000 использует HTTP; для публичной передачи данных отдельно настройте защищённый транспорт.

Приватный Docker Registry v2 создаётся панелью и использует htpasswd-аутентификацию. Порт задаётся `REGISTRY_PORT`; реквизиты отображаются администратору. Базовая конфигурация реестра — HTTP: это не следует считать защищённым внешним транспортом без дополнительной настройки.

### Почта, внешние серверы, балансировка

Почта обслуживается Docker Mailserver, веб-почта — Roundcube. Для доставки в интернет отдельно настройте DNS, MX/SPF/DKIM/DMARC, обратную запись адреса, TLS почтовых протоколов и разрешённый исходящий SMTP. HTTPS вебмейла не означает, что IMAP/SMTP уже защищены TLS.

Внешние серверы добавляются по SSH; предусмотрено подключение через bastion/jump host. Это уже существующие серверы, не ВМ, создаваемые в KubeVirt.

Балансировщик генерирует конфигурацию хостового Nginx для выбранных ВМ. Доступен администратору, так как занимает порты всего сервера.

Алерты проверяют доступность и CPU/RAM ВМ или хоста и отправляют уведомления в Telegram/webhook. Проекты дают общий доступ к ресурсам по ролям наблюдателя, редактора и владельца.

## Домены и доступ из интернета

### Служебные и пользовательские домены

Служебные переменные:

~~~dotenv
PANEL_DOMAIN=panel.example.com
MAIL_DOMAIN=mail.example.com
STORAGE_DOMAIN=storage.example.com
RABBITMQ_DOMAIN=queue.example.com
ACME_EMAIL=admin@example.com
~~~

Каждый домен необязателен. Мастер настройки:

~~~bash
sudo bash scripts/add-domain.sh
~~~

Пользовательские домены создаются в «Домены и TLS». Проверяются A-запись и подтверждение владения TXT `_aegis-challenge.<домен>`. При наличии подходящего DNS API-токена панель может создавать записи автоматически.

Caddy выпускает сертификаты и проксирует HTTP/HTTPS-трафик. Для пользовательских доменов публично доступного хоста используется HTTP-01; для DNS-01 поддерживаются Timeweb Cloud и Cloudflare. Служебные домены из `.env` в текущей реализации добавляются в Caddy только с DNS API-токеном и используют DNS-01. Если заданы оба DNS-токена, выбирается Cloudflare:

~~~dotenv
TIMEWEB_DNS_API_TOKEN=
CLOUDFLARE_DNS_API_TOKEN=
~~~

Задайте только нужный токен с правами для вашей DNS-зоны. Не публикуйте `.env` и Caddy-конфигурацию с секретами.

DNS-01 может выпустить сертификат для хоста за NAT, но **не делает сервер доступным из интернета**. Нужны маршрутизация, проброс или туннель. Изменение DNS и выпуск сертификата занимают время, но ожидание не исправляет неверный endpoint, отсутствие службы или закрытый порт.

### Публичный IP и домашний NAT

При наличии публичного IP направьте DNS на него и разрешите нужные порты. За NAT укажите внешний адрес в `AEGIS_HOST_IP` и настройте проброс на роутере.

Для панели через Caddy используются 80/443; для ВМ с прямыми внешними портами нужно отдельно открыть соответствующие TCP-порты. Обычный HTTP reverse proxy не заменяет SSH, RDP или протокол PostgreSQL/MySQL.

Если сервер за CGNAT, обычный проброс на домашнем роутере сам по себе не обеспечит входящее подключение.

### Cloudflare Tunnel

В Compose есть необязательный сервис `cloudflared`:

~~~dotenv
CLOUDFLARE_TUNNEL_TOKEN=<токен-туннеля>
COMPOSE_PROFILES=cloudflare
~~~

После настройки публичного hostname и upstream в Cloudflare:

~~~bash
docker compose up -d cloudflared
docker compose logs --tail 100 cloudflared
~~~

Для панели используется upstream `http://localhost:8081`, вебмейла — `:8082`, консоли MinIO — `:9001`. По умолчанию это публикация веб-интерфейсов; она не создаёт автоматически публичный TCP-проброс SSH/RDP или всех портов ВМ.

DNS API-токен и токен Tunnel — разные секреты. Для работы вне локальной сети проверьте также, куда разрешается домен на клиентском компьютере.

## Конфигурация

Основной файл — `.env`. Шаблон — [.env.example](.env.example). Compose требует служебные пароли без небезопасной подстановки общеизвестных значений; все `CHANGE_ME` нужно заменить при ручной настройке.

| Переменная | Для чего |
|---|---|
| `ADMIN_TOKEN` | Административный API-токен и первоначальный пароль нового пользователя admin |
| `AEGIS_SECRET_KEY` | Шифрование хранимых секретов; сохраняйте неизменным вместе с БД |
| `POSTGRES_PASSWORD`, `DATABASE_URL`, `DB_CONN_STR` | Системная БД и подключения Python/Go; пароли должны совпадать |
| `RABBITMQ_USER`, `RABBITMQ_PASS`, `RABBITMQ_URL` | Очередь задач и учётные данные |
| `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD` | S3-доступ backend/worker и MinIO; значения должны совпадать во всех трёх сервисах |
| `MARIADB_ROOT_PASSWORD` | Служебная MariaDB |
| `STORAGE_CLASS` | Класс системных PVC ВМ и БД |
| `NETWORK_STORAGE_CLASS` | Отдельный класс сетевых LVM-дисков |
| `AEGIS_HOST_IP` | Адрес хоста для внешних ссылок и интеграций; важен при NAT |
| `REGISTRY_PORT` | Порт приватного реестра, по умолчанию 5000 |
| `AEGIS_CORS_ORIGINS` | Разрешённые источники CORS; для своей установки можно ограничить доменами панели |
| Домены, DNS API и Tunnel | Необязательные настройки из предыдущего раздела |

`AEGIS_LVM_POOL_GB` задаёт размер пула при отдельном запуске LVM-скрипта; пример параметра находится в самом скрипте. Не используйте этот параметр как способ переинициализировать действующее хранилище.

Не меняйте `AEGIS_SECRET_KEY` без отдельного плана ротации: существующие секреты перестанут расшифровываться. На старых установках без отдельного ключа шифрование выводится из `ADMIN_TOKEN`, поэтому его смена также может нарушить доступ к секретам.

Изменение окружения требует **пересоздания контейнера**, а не только `docker compose restart`:

~~~bash
docker compose up -d --no-deps --force-recreate backend worker
~~~

Если менялись S3/RabbitMQ/PostgreSQL-пароли, отдельно согласуйте изменения с самими сервисами и их состоянием. Изменение `.env` не является универсальной миграцией паролей во всех существующих БД и аккаунтах.

### Основные порты хоста

| Порт | Сервис | Доступ по конфигурации проекта |
|---|---|---|
| 8080 / 8443 | Панель: HTTP redirect / HTTPS | Прямой доступ к хосту |
| 8081 | HTTP upstream панели | Только loopback |
| 80 / 443 | Caddy, доменные сайты | При работающем Caddy |
| 8000 / 8001 | FastAPI / Go API | Host network; ограничьте внешний доступ фаерволом |
| 5432 / 3306 | Служебные PostgreSQL / MariaDB | Только 127.0.0.1 в Compose |
| 5672 / 15672 | RabbitMQ / веб-консоль | Только 127.0.0.1 в Compose |
| 9000 | MinIO S3 API | Опубликован на хосте, нужен также импортам CDI |
| 9001 | Консоль администратора MinIO | Только 127.0.0.1 в Compose |
| 8082 | Roundcube | Опубликован на хосте |
| 25 / 143 / 587 / 993 | Почтовые протоколы | Опубликованы; готовность/TLS настраиваются отдельно |
| 5000 по умолчанию | Docker Registry | Если создан панелью |
| Вычисляемые порты ВМ | SSH/HTTP/HTTPS/RDP/приложения | По настроенным DNAT и белым спискам |

Пример доступа к loopback-консоли MinIO через SSH-туннель с вашего компьютера:

~~~bash
ssh -L 19001:127.0.0.1:9001 'root@<адрес-хоста>'
~~~

Пока SSH-сессия открыта, консоль доступна на `http://127.0.0.1:19001`. Это учётная запись MinIO, а не пароль пользователя панели.

## Пользователи и безопасность

У панели есть системные роли `admin` и `student`. Администратор создаёт пользователей и задаёт лимиты CPU, RAM, ВМ и дискового пространства. Проверки доступа и квот выполняются в API; скрытые кнопки интерфейса не заменяют авторизацию.

Дополнительно реализованы:

- хэширование паролей пользователей, ограничение неудачных входов;
- 2FA/TOTP и резервные коды;
- подписанные сессионные токены и персональные API-токены `aeg_...`;
- хранение API-токенов в виде хэша; полный токен показывается при создании;
- Fernet-шифрование ряда служебных секретов в БД;
- проектные роли и проверки владельца ресурса;
- политики бакетов S3 и ограничения доступа к приватным БД;
- валидация пользовательского ввода, защита отдельных сетевых интеграций от SSRF;
- журнал аудита и маскирование внутренних 5xx-ошибок с кодом обращения.

Это не обещание отсутствия уязвимостей. Backend/worker имеют административный доступ к хосту, Docker и Kubernetes. Компрометация панели или её секретов может привести к компрометации сервера.

Для установки используйте отдельный хост, HTTPS, защищённый SSH и ограничение внешних административных портов. Не публикуйте kubeconfig, приватные SSH-ключи, дампы БД, `.env`, S3 secret key или presigned URL.

Файлы пользовательских образов — не место для конфиденциальных резервных копий: каталог образов раздаётся отдельным static endpoint.

MinIO на том же физическом хосте — удобное место хранения, но не независимая аварийная копия. Для защиты от потери сервера нужен отдельный план копирования данных и метаданных на другой носитель/сервер.

## Обновление и автозапуск

### Обновление

Перед обновлением сохраните системную БД, `.env`, пользовательские данные и конфигурацию хоста. Работы планируйте вне активного копирования/восстановления ВМ.

Пример сохранения метаданных панели от root из каталога проекта:

~~~bash
umask 077
task_backup_dir=$(mktemp -d /root/hosting-upgrade.XXXXXX)
install -m 600 .env "$task_backup_dir/env"
docker compose exec -T db pg_dump -U postgres -d aegis > "$task_backup_dir/aegis.sql"
~~~

Это **не полная резервная копия хостинга**: отдельно нужны данные PVC, MinIO, почты и другие постоянные данные. Храните копию ключа шифрования вместе с восстановимой копией БД, но не публикуйте её.

Обновление основных сервисов:

~~~bash
cd /root/Hosting
git status --short
git pull --ff-only
docker compose up -d --build --no-deps backend worker frontend
docker compose ps
curl -fsS http://127.0.0.1:8000/
~~~

При локальных изменениях сначала разберите их; не используйте `git reset --hard` для принудительного обновления.

Если изменились другие сервисы или весь Compose, после проверки конфигурации используйте `docker compose up -d --build`. Обычный restart не применяет новое окружение и не заменяет собранный образ.

Backend создаёт/обновляет схему системной БД при запуске; worker ждёт готовности схемы. Не удаляйте Docker volumes или PVC для исправления обычной ошибки запуска. Старую S3-установку при необходимости дополните `scripts/enable-vm-export.sh`.

После обновления перезагрузите страницу браузера. Новые шаблоны cloud-init не меняют уже созданных гостей.

### Автозапуск и постоянные данные

Установщик регистрирует:

- `aegis-network.service` — восстановление сетевого моста;
- `aegis-hosting.service` — запуск Compose;
- `aegis-lvm-loop.service` — восстановление loop/LVM при соответствующей установке;
- `aegis-lvm-thin-monitor.timer` — мониторинг thin-pool.

Docker и K3s должны быть включены в автозапуск. Контейнеры Compose используют `restart: unless-stopped`; вручную остановленные сервисы могут не подняться автоматически.

Проверка:

~~~bash
systemctl status docker k3s aegis-network.service aegis-hosting.service --no-pager
systemctl status aegis-lvm-loop.service aegis-lvm-thin-monitor.timer --no-pager
~~~

Автозапуск панели не означает автоматический запуск всех остановленных ВМ: учитывается желаемое состояние машины и runStrategy.

Постоянные данные распределены между Docker volumes, Kubernetes PVC, файлами LVM, каталогом `data/` и `mail-config/`. Сертификаты Caddy хранятся в отдельном volume. Каталог исходников — не единственное место, которое нужно сохранять.

## Диагностика

Все команды ниже выполняются на сервере hosting, если отдельно не указано «внутри ВМ». Заменяйте значения в угловых скобках своими; это обозначения, а не готовые адреса/имена. Не передавайте вместе с логами пароли, токены, kubeconfig или приватные ключи.

### Базовая проверка

~~~bash
cd /root/Hosting
docker compose ps
docker compose logs --since 15m --tail 150 backend worker
kubectl get nodes
kubectl get pods -A
kubectl get vm,vmi -A
kubectl get pvc -A -o wide
df -h / /var/lib
~~~

Для сообщения «Внутренняя ошибка сервера. Код обращения: …» найдите соответствующий traceback:

~~~bash
docker logs hosting-backend --since 30m 2>&1 | grep -F -C 20 '<код-обращения>'
~~~

### ВМ запущена, но недоступна

~~~bash
kubectl describe vmi '<имя-ВМ>' -n default
sudo iptables -t nat -S PREROUTING
sudo iptables -S FORWARD
~~~

Проверьте последовательно гостевой IP, внутренний сервис/порт, DNAT, белый список, фаервол хоста, роутер и DNS клиентского компьютера. Не подменяйте IP гостя его Docker bridge или адресом хоста.

Для Proxmox **внутри установленной ВМ через VNC**:

~~~bash
ip -br a
systemctl status pveproxy --no-pager
ss -lntp | grep ':8006'
~~~

При SSH-ошибке `Permission denied (publickey)` проверьте пользователя и соответствие приватного ключа публичному. `Connection refused` — отсутствие слушателя/доступного проброса, а не неправильный ключ.

### Сетевой диск Pending или не виден в госте

~~~bash
kubectl get pvc -A -o wide
kubectl get datavolumes -A
kubectl describe pvc '<имя-PVC>' -n default
kubectl describe datavolume '<имя-PVC>' -n default
kubectl get pods -A | grep -E 'openebs|cdi|importer'
sudo vgs --units g -o vg_name,vg_size,vg_free
sudo lvs --units g -o vg_name,lv_name,lv_size,data_percent,metadata_percent
~~~

Для `WaitForFirstConsumer` PVC может ожидать потребителя. Появление prime-PVC или импортирующего пода ещё не означает готовность конечного тома: смотрите events и состояние DataVolume.

Если импортёр не может открыть блочное устройство с `Permission denied`, проверяйте права устройств в containerd/K3s, в том числе поддержку `nonroot-devices`:

~~~bash
k3s server --help | grep -F nonroot-devices
grep -n 'device_ownership_from_security_context' /var/lib/rancher/k3s/agent/etc/containerd/config.toml
~~~

Не форматируйте и не удаляйте PVC ради обхода ошибки доступа. Изменение конфигурации K3s и его перезапуск планируйте отдельно, поскольку это затрагивает работающий кластер.

Если OpenEBS ещё не установлен:

~~~bash
sudo bash scripts/install-openebs-lvm.sh
~~~

Перед отдельным запуском проверьте параметры размера и состояние существующего пула. [docs/LVM_RESET.md](docs/LVM_RESET.md) описывает отдельную процедуру сброса; это удаление данных, а не обычное обновление.

### Ошибка бэкапа или снимка

~~~bash
docker compose logs --since 30m --tail 400 worker
kubectl get virtualmachineexports -A
kubectl get datavolumes -A
docker compose exec -T backend mc --version
docker compose exec -T worker mc --version
~~~

- `SignatureDoesNotMatch`: проверьте совпадение S3-учётных данных backend, worker и MinIO; после изменения окружения пересоздайте нужные контейнеры. Ошибка подписи не означает, что бакет отсутствует.
- `exec format error` у `mc`: пересоберите backend/worker с исправной утилитой под архитектуру образа.
- Зависание на импорте/откате: проверяйте DataVolume, доступ из подов к MinIO и свободное место. Не снимайте блокировки и не удаляйте исходные диски вручную.
- Статус «Не удался» не превращается в готовую копию от смены пароля: после исправления причины создайте новую копию.

### Домены и сертификаты

~~~bash
docker logs aegis-caddy --tail 150
docker compose logs --tail 100 cloudflared
~~~

Эти контейнеры могут отсутствовать, если соответствующий режим не настроен. Проверьте DNS, выбранный токен провайдера, адрес upstream и доступность самого приложения. Ошибка TLS не всегда исправляется ожиданием сертификата.

### SQL-консоль

Если появляется `No such file or directory: kubectl`, используется старый образ backend/worker без утилиты. Обновите исходники и пересоберите контейнеры:

~~~bash
docker compose up -d --build --no-deps backend worker
~~~

### Backend

Используйте отдельное Python-окружение; контейнер backend собирается на Python 3.11:

~~~bash
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements-dev.txt
.venv/bin/python -m pytest -q backend/tests
~~~

Тестовое окружение настраивается в `backend/tests/conftest.py`. Большинство интеграций заменено fake/mock-реализациями; unit-тесты не доказывают готовность конкретного удалённого сервера. Для проверки реальной установки используйте тестовую ВМ и эксплуатационные команды выше.

### Frontend

~~~bash
cd frontend
npm ci
node --test tests/*.test.js
npm run build
~~~

Docker-сборка frontend использует Node.js 20. Для разработки интерфейса доступно `npm run dev`; Vite dev server не заменяет установленный серверный стек.

### API, CLI и Terraform

Схема API: `/api/openapi.json`; Swagger backend: `/docs` на его адресе. Обычная панель проксирует маршруты `/api`; внешний административный порт backend не нужно открывать ради CLI.

CLI работает с тем же API. Пример с персональным токеном через HTTPS:

~~~bash
python3 cli/aegis configure --url https://panel.example.com --token '<персональный-API-токен>'
python3 cli/aegis vm list
~~~

Не сохраняйте реальные токены в публичных примерах или истории демонстраций. Подробности: [cli/README.md](cli/README.md).

Terraform-провайдер поддерживает ресурсы ВМ и БД и data source ВМ. Он собирается локально, публичный реестр провайдера не используется. Изменение параметров создания `aegis_vm` требует пересоздания; перед apply проверяйте план.

Документация: [terraform-provider-aegis/README.md](terraform-provider-aegis/README.md). Пример: [examples/main.tf](terraform-provider-aegis/examples/main.tf).

## Ограничения

- Установка требует интернета и доступа к сторонним источникам пакетов/образов; полноценная offline-сборка не подготовлена.
- Windows, Proxmox и TrueNAS требуют установки с ISO и настройки внутри гостя.
- Собственный SSH-ключ требует соответствующего приватного файла на клиентском компьютере; команда в панели не заменяет ключ.
- Дополнительный PVC не расширяет системный раздел и не монтируется/форматируется автоматически.
- S3-снимки — полные копии с простоем, не live snapshots и не снимки RAM.
- Локальные PVC и MinIO на одном хосте не дают сами по себе HA или независимую аварийную копию.
- HTTPS веб-панели не означает TLS на всех S3, Registry, почтовых и пользовательских сервисах.
- Cloudflare Tunnel для веб-панели не открывает автоматически все TCP-порты ВМ.
- Go HCI-компонент содержит демонстрационные модели/метрики и элементы биллинга. Это не подтверждение готового коммерческого платёжного или DDoS-защитного сервиса.
- Наличие тестов и проверок доступа не заменяет аудит безопасности и проверку восстановления на вашей инфраструктуре.

Перед размещением важных данных проверьте полный цикл: создание тестовой ВМ → доступ → подключение диска → копирование в S3 → изменение данных → восстановление → проверка после перезагрузки хоста.
