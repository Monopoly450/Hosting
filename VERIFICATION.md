# Чеклист живой проверки

Функции, добавленные последними (маркетплейс, реестр образов, домены с TLS,
проекты, алерты, бэкапы по расписанию), покрыты юнит-тестами, но **на реальном
кластере не запускались**. Тесты проверяют логику — они не докажут, что
контейнер поднимется, образ скачается, а сертификат выпустится.

Этот чеклист — минимальный проход, который ловит именно такие сбои. Проходите
по порядку: каждый следующий блок опирается на предыдущий.

> Все команды выполняются **на хост-сервере**, из каталога проекта.

---

## 0. Обновление и базовая проверка

```bash
git pull
```

Убедитесь, что в `.env` есть все обязательные переменные (иначе compose
намеренно откажется стартовать):

```bash
for v in POSTGRES_PASSWORD RABBITMQ_USER RABBITMQ_PASS RABBITMQ_URL \
         MINIO_ROOT_PASSWORD MARIADB_ROOT_PASSWORD ADMIN_TOKEN \
         DB_CONN_STR DATABASE_URL AEGIS_SECRET_KEY; do
  grep -q "^$v=" .env || echo "НЕ ХВАТАЕТ: $v"
done
```

Недостающие сгенерируйте (`openssl rand -hex 24`) — подробности и нюансы смены
паролей уже созданной БД описаны в `university_update_guide.md`.

Пересборка обязательна: добавились зависимости `qrcode`, `dnspython`, `bcrypt`.

```bash
docker compose up -d --build
docker compose ps          # все сервисы healthy / running
docker compose logs backend --tail=50 | grep -iE "error|traceback" || echo "ошибок при старте нет"
```

**Ожидается:** backend поднялся, в логах нет трейсбеков, миграции применились
(таблицы `projects`, `domains`, `alert_rules` создаются автоматически).

```bash
curl -s localhost:8000/ | head -c 200        # {"status":"online",...}
```

- [ ] Панель открывается, вход работает

## 1. Определение внешнего IP

Это фундамент для трёх функций сразу (маркетплейс, реестр, домены) — раньше
здесь была ошибка, из-за которой они молча не работали.

```bash
docker compose exec backend python -c \
  "from app.core.netutils import detect_host_ip; print(detect_host_ip())"
```

**Ожидается:** реальный адрес сервера, **не** `127.0.0.1`.
Если адрес неверный (сервер за NAT) — задайте `AEGIS_HOST_IP` в `.env` и
перезапустите: `docker compose up -d`.

- [ ] IP определяется правильно

## 2. Реестр образов

Вкладка **«Контейнерный реестр»** → «Запустить реестр».

```bash
docker ps --filter name=aegis-registry     # контейнер поднялся
```

Реестр теперь **с паролем**. Логин и пароль показаны на вкладке. Проверка
push с любой машины, где есть Docker:

```bash
HOST=<IP сервера>:5000

# Реестр работает по HTTP — добавьте его в insecure-registries:
#   /etc/docker/daemon.json → {"insecure-registries": ["<IP сервера>:5000"]}
#   sudo systemctl restart docker

docker login $HOST -u aegis            # пароль — со вкладки реестра
docker pull alpine:latest
docker tag alpine:latest $HOST/test-image:v1
docker push $HOST/test-image:v1
```

**Ожидается:** push проходит; образ появился в списке репозиториев на вкладке.
Проверьте, что **без** авторизации доступа нет:

```bash
docker logout $HOST
curl -s -o /dev/null -w "%{http_code}\n" http://$HOST/v2/_catalog   # ожидается 401
```

- [ ] Push работает после `docker login`
- [ ] Без авторизации — 401
- [ ] Удаление тега из панели работает

## 3. Маркетплейс приложений

Вкладка **«Маркетплейс»** → установите **Uptime Kuma** (самое лёгкое: один
контейнер, без БД, быстро стартует).

```bash
# следим за созданием ВМ
docker compose logs worker -f --tail=30
```

**Ожидается:** ВМ создаётся, через 1–3 минуты статус `Running`.
Дальше — самое важное, чего не проверяют юнит-тесты: **действительно ли внутри
ВМ поднялся docker compose**.

```bash
VM=<имя ВМ из панели>
kubectl get vmi $VM                                    # Running
# зайдите в ВМ по SSH (адрес и порт — на вкладке «Деплой приложений»)
ssh ubuntu@<IP сервера> -p <SSH-порт из панели>
  sudo cloud-init status --long                        # done, без ошибок
  sudo docker compose -f /opt/app/docker-compose.yml ps  # контейнеры Up
  cat /opt/app/.env                                    # PUBLIC_URL с реальным IP
```

Затем откройте ссылку приложения из панели в браузере.

**Ожидается:** приложение отвечает по адресу `http://<IP сервера>:280XX`.

Отдельно проверьте приложение, которому нужен свой URL, — **WordPress** или
**Ghost**: у них ссылки генерируются из `PUBLIC_URL`, и раньше они указывали на
localhost.

- [ ] ВМ создалась, cloud-init отработал без ошибок
- [ ] Контейнеры внутри ВМ запущены
- [ ] Приложение открывается по ссылке из панели
- [ ] У Ghost/WordPress ссылки ведут на реальный адрес, а не на localhost

## 4. Домены и TLS

Нужны: реальный домен и открытые снаружи порты **80 и 443**.

```bash
# порт 80 не должен быть занят (дефолтный сайт nginx мы отключаем)
sudo ss -tlnp | grep -E ':80 |:443 '
```

Вкладка **«Домены и TLS»** → добавьте домен, указав целью приложение из шага 3.

Панель покажет **две записи**, которые надо создать у регистратора:

| Тип | Имя | Значение |
|-----|-----|----------|
| TXT | `_aegis-challenge.<домен>` | токен со вкладки |
| A   | `<домен>` | IP сервера |

TXT подтверждает владение доменом — без неё домен нельзя увести на чужую ВМ.

```bash
# проверяем, что DNS разъехался (может занять до нескольких часов)
dig +short TXT _aegis-challenge.<домен>
dig +short A <домен>
```

Когда обе записи видны — нажмите «Проверить» в панели.

```bash
docker ps --filter name=aegis-caddy
docker logs aegis-caddy --tail=50 | grep -iE "certificate|error"
```

**Ожидается:** статус «активен (TLS)», Caddy получил сертификат.

```bash
curl -sI https://<домен> | head -3       # HTTP/2 200
```

> Если сертификат не выпускается — почти всегда причина в том, что порт 80
> недоступен снаружи (firewall/провайдер) или A-запись ещё не разошлась.
> У Let's Encrypt есть лимиты на неудачные попытки — не долбите «Проверить»
> подряд, дождитесь DNS.

- [ ] TXT-проверка владения проходит
- [ ] Сертификат выпущен, сайт открывается по HTTPS
- [ ] Без TXT-записи домен **не** попадает в проксирование

## 5. Бэкапы по расписанию

Вкладка **«Бэкапы по расписанию»** → создайте расписание для ВМ и нажмите
«Запустить сейчас» (не дожидаясь срока).

```bash
kubectl get datavolumes | grep backup     # появился клон диска
docker compose logs worker --tail=30 | grep -i backup
```

Для базы данных бэкап уходит в MinIO:

```bash
docker compose exec minio mc ls local/database-backups/ 2>/dev/null \
  || echo "проверьте через веб-консоль MinIO (SSH-туннель на 9001)"
```

- [ ] Ручной запуск создаёт копию
- [ ] Поле «последний запуск» обновилось
- [ ] Ротация: при retention=1 старые копии удаляются

## 6. Алерты

Вкладка **«Алерты»** → создайте канал (webhook удобно проверять через
`webhook.site`) и нажмите «Тест».

**Ожидается:** тестовое сообщение доставлено.

Затем создайте правило «ВМ упала» на тестовую ВМ и выключите её:

```bash
virtctl stop <имя ВМ>     # или кнопкой в панели
```

**Ожидается:** в течение минуты правило переходит в «сработал» и приходит
уведомление. После запуска ВМ — «восстановлен» (уведомление приходит только на
смену состояния, повторов быть не должно).

Проверьте, что защита от SSRF работает — такой канал создаться **не должен**:

```
http://169.254.169.254/latest/meta-data/     → ошибка «внутренняя сеть»
http://localhost:8000/api/auth/users         → ошибка
```

- [ ] Тестовое уведомление доходит
- [ ] Алерт срабатывает и восстанавливается
- [ ] Webhook на внутренний адрес отклоняется

## 7. Проекты и роли (RBAC)

Создайте второго пользователя, проект, добавьте его как **наблюдателя** и
привяжите к проекту свою ВМ.

Войдите под вторым пользователем:

- [ ] Чужая ВМ видна в списке
- [ ] Детали ВМ открываются
- [ ] Кнопки удаления/перезапуска дают **403** (наблюдатель не меняет ресурсы)
- [ ] После смены роли на «редактор» управление появляется

Это ключевая гарантия RBAC: `viewer` видит, но не может изменить.

## Что делать при сбое

```bash
docker compose logs backend --tail=100
docker compose logs worker --tail=100
```

Серверные ошибки теперь не показывают внутренние детали в интерфейсе, а выдают
**код обращения**. Полный текст ищется в логах по этому коду:

```bash
docker compose logs backend | grep <код из сообщения>
```
