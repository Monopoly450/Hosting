# Руководство по обновлению сервера хостинга в университете

В этом документе описаны изменения и приведена подробная инструкция по обновлению вашего основного сервера в университете.

---

## 🆕 Последнее обновление: сеть, клонирование, деплой из GitHub, шаблоны

### Что нового
1. **Стабильный IP виртуалок (не меняется после перезагрузки).** Каждая новая ВМ получает постоянный статический адрес на мосту `br-vms` (`172.20.0.<30 + ID%200>`) через второй сетевой интерфейс. Pod-сеть остаётся для интернета как страховка.
2. **Стабильные внешние порты + рабочий проброс.** Внешний порт считается от ID ВМ (не меняется), а фоновый демон в воркере переустанавливает проброс при смене IP — форвардинг сам восстанавливается после перезагрузок.
3. **Стабильный MAC-адрес** у каждой ВМ (детерминирован от имени).
4. **Клонирование ВМ** — кнопка «Клонировать» на карточке создаёт полную копию (диск + настройки) как новую ВМ.
5. **Вкладка «Деплой приложений»** — разворачивает приложение из GitHub-репозитория на отдельной выделенной ВМ (стеки: Docker Compose, Dockerfile, Node.js, Python, статика, своя команда).
6. **Новые шаблоны окружения** при создании ВМ: LEMP, Portainer, Python (venv+gunicorn), PostgreSQL, Redis; Node.js обновлён до 20 LTS.

### Как обновить под эти функции

> [!IMPORTANT]
> **Шаг A (один раз). Пере-примените сетевой мост `bridge-network`** — теперь он без авто-раздачи IP (чтобы статические адреса ВМ не конфликтовали). Без этого шага новые ВМ могут получать конфликтующие адреса.
> ```bash
> cat <<'EOF' | kubectl apply -f -
> apiVersion: "k8s.cni.cncf.io/v1"
> kind: NetworkAttachmentDefinition
> metadata:
>   name: bridge-network
>   namespace: default
> spec:
>   config: '{ "cniVersion": "0.3.1", "name": "bridge-network", "type": "bridge", "bridge": "br-vms", "isGateway": false, "ipam": {} }'
> EOF
> ```
> Полный `bootstrap-host.sh` гонять не нужно — он уже содержит эту конфигурацию для новых установок, а на работающем сервере достаточно команды выше.

**Шаг B. Обновите панель:**
```bash
cd ~/Hosting
git pull
docker compose up -d --build
```
Новая таблица `app_deployments` и колонка `static_ip` создадутся автоматически при старте — ручных миграций не нужно.

### Что важно учесть
* **Стабильный IP получат только НОВЫЕ ВМ.** У уже существующих останется старый pod-адрес — чтобы дать им стабильный IP, пересоздайте их или используйте «Клонировать».
* Проверка: создайте тестовую ВМ, в её деталях поле **«Локальный IP (Bridge)»** должно стать `172.20.0.x` и не меняться после стоп/старта.
* Если bridge-интерфейс не поднимется — ВМ всё равно останется с интернетом (pod-сеть), а проброс откатится на pod-адрес. Диагностика: `kubectl get vmi <имя> -o wide` и `docker compose logs worker | tail`.
* Деплой из GitHub работает с **публичными** репозиториями (без токена).

## Что было сделано ранее (обновление безопасности):

1. **Шифрование секретов в базе данных**:
   * Пароли внешних SSH-серверов, пароли пользовательских баз данных и секретные ключи S3 больше не хранятся в открытом виде. Добавлен модуль `backend/app/core/crypto.py` (шифрование Fernet).
   * Ключ шифрования берётся из новой переменной `AEGIS_SECRET_KEY`. Если она не задана — ключ выводится из `ADMIN_TOKEN` (старые установки продолжат работать без правки `.env`).
   * При первом запуске бэкенд **автоматически дошифрует** секреты, которые уже лежат в базе в открытом виде. Вручную ничего делать не нужно.
   * ⚠️ После первого запуска менять `AEGIS_SECRET_KEY` (и `ADMIN_TOKEN`, если ключ выводится из него) **нельзя** — старые секреты перестанут расшифровываться.

2. **Служебные порты закрыты от внешнего доступа**:
   * PostgreSQL (5432), RabbitMQ (5672 / 15672), MariaDB (3306) и консоль MinIO (9001) теперь слушают **только 127.0.0.1**. Снаружи, в том числе с белого IP, они больше не доступны.
   * S3 API (9000) и почтовые порты остались публичными — это рабочая функциональность.
   * Для доступа к веб-консолям MinIO/RabbitMQ с рабочей машины используйте SSH-туннель, например: `ssh -L 9001:127.0.0.1:9001 root@<IP_СЕРВЕРА>`.

3. **Параметризованы учётные данные RabbitMQ**:
   * Логин/пароль очереди задаются через `RABBITMQ_USER` / `RABBITMQ_PASS` в `.env` (по умолчанию `guest`/`guest`, который RabbitMQ и так пускает только с localhost).

4. **Единый механизм миграций БД**:
   * Все `ALTER TABLE`-миграции вынесены в общий модуль `backend/app/core/migrations.py`, который используется и при старте бэкенда, и скриптом `run_migrations.py` (раньше было два расходящихся списка).

5. **Удалён мёртвый код**:
   * Из `databases.py` убраны неиспользуемые функции доступа к общим СУБД (пользовательские БД давно работают в изолированных подах Kubernetes).

6. **Добавлены автотесты бэкенда**:
   * В `backend/tests/` появились тесты модулей шифрования и авторизации (13 тестов). Запуск: `cd backend && pip install -r requirements-dev.txt && pytest tests/`.

7. **Обновлена документация**:
   * Из `README.md` убраны реальные пароли; в `.env.example` все секреты заменены на `CHANGE_ME` с инструкцией `openssl rand -hex 24`.

## Инструкция по обновлению сервера в университете:

Выполните эти шаги по очереди в терминале вашего сервера в университете:

### Шаг 1. Перейдите в рабочую папку и загрузите обновления из GitHub
```bash
cd ~/Hosting
git pull
```

### Шаг 2. ⚠️ Добавьте ключ шифрования секретов в `.env` (обязательно, выполняется один раз)
Откройте файл `.env` и добавьте строку с новым ключом. Сгенерировать надёжное значение:
```bash
openssl rand -hex 24
```
Затем впишите его в `.env`:
```env
AEGIS_SECRET_KEY=<вставьте_сгенерированное_значение>
```
> [!IMPORTANT]
> Если пропустить этот шаг, ключ будет выведен из `ADMIN_TOKEN` — всё заработает, но тогда **менять `ADMIN_TOKEN` в будущем будет нельзя**, иначе сохранённые пароли перестанут расшифровываться. Рекомендуется задать отдельный `AEGIS_SECRET_KEY`.
>
> Значение `AEGIS_SECRET_KEY` **нельзя менять** после первого запуска — запишите его в надёжное место.

### Шаг 3. Включите горячую замену дисков в KubeVirt (выполняется один раз на сервере)
```bash
kubectl patch kubevirt kubevirt -n kubevirt --type merge -p '{"spec":{"configuration":{"developerConfiguration":{"featureGates":["LiveMigration","SRIOV","NUMA","GPUDevice","HotplugVolumes","DeclarativeHotplugVolumes"]}}}}'
```

### Шаг 4. Примените обновлённую службу автозапуска LVM
Запустите скрипт установки хранилища LVM, чтобы обновить конфигурацию службы автозапуска:
```bash
sudo bash ./scripts/install-openebs-lvm.sh
```
> [!NOTE]
> Если при создании диска в будущем вы увидите статус Pending, а в выводе `kubectl describe pvc` будет ошибка `exit status 5`, это означает, что в системе зависли дубликаты loop-устройств. Очистите их следующими командами:
> ```bash
> sudo vgchange -an vg-aegis
> sudo losetup -D
> sudo systemctl restart aegis-lvm-loop.service
> ```

### Шаг 5. Пересоберите и запустите контейнеры Docker
Добавилась зависимость `cryptography`, поэтому обязательно с флагом `--build`:
```bash
docker compose up -d --build
```

## Обновление до версии с проектами, доменами, реестром и маркетплейсом

Появились зависимости `qrcode` (QR для 2FA), `dnspython` (проверка владения
доменом) и `bcrypt` (пароль реестра образов), поэтому обновляться нужно
**обязательно с `--build`**:
```bash
git pull
docker compose up -d --build
```

> ### ⚠️ Обязательные пароли в `.env` (ломающее изменение)
>
> Раньше `docker-compose.yml` при отсутствии переменной молча подставлял пароль
> по умолчанию: RabbitMQ `guest/guest`, MinIO `minioadmin-secret-2026`,
> MariaDB `mariadb-root-secret-2026`, PostgreSQL `postgres`. Все они
> **опубликованы в этом репозитории**, то есть общеизвестны. Особенно опасен
> MinIO: его S3-порт 9000 открыт наружу, а в нём лежит бакет
> `database-backups` с дампами пользовательских БД.
>
> Теперь эти переменные обязательны — без них compose **не запустится** и
> сообщит, какой именно не хватает. Проверьте свой `.env`:
> ```bash
> for v in POSTGRES_PASSWORD RABBITMQ_USER RABBITMQ_PASS RABBITMQ_URL \
>          MINIO_ROOT_PASSWORD MARIADB_ROOT_PASSWORD ADMIN_TOKEN \
>          DB_CONN_STR DATABASE_URL; do
>   grep -q "^$v=" .env || echo "НЕ ХВАТАЕТ: $v"
> done
> ```
> Недостающие добавьте со сгенерированными значениями (`openssl rand -hex 24`).
> Учтите при смене паролей:
> * **RabbitMQ** — тома нет, новый пользователь создастся при пересоздании
>   контейнера. Пароль в `RABBITMQ_PASS` и внутри `RABBITMQ_URL` должны совпадать.
> * **PostgreSQL и MariaDB** — пароль применяется только при первичной
>   инициализации тома. Если БД уже создана, смените пароль внутри неё:
>   `docker exec -it aegis-db psql -U postgres -c "ALTER USER postgres PASSWORD '<новый>';"`
>   и синхронно обновите `DATABASE_URL` и `DB_CONN_STR`.
> * **MinIO** — читает переменные при каждом старте, достаточно задать новый
>   пароль и перезапустить контейнер.

> **Реестр образов теперь с паролем.** Раньше `aegis-registry` работал без
> аутентификации — кто угодно, кто дотягивался до порта, мог пушить и удалять
> образы. Теперь при запуске реестра генерируется пароль (логин `aegis`), он
> показан на вкладке «Контейнерный реестр». Перед push выполните
> `docker login <хост>:5000 -u aegis`. Если реестр был запущен старой версией,
> нажмите «Остановить» и «Запустить» ещё раз — контейнер пересоздастся с
> аутентификацией (загруженные образы в томе сохранятся).

Новые таблицы (`projects`, `domains`, `alert_rules`, `backup_schedules`, `api_tokens` и
другие) и колонки создаются автоматически при старте бэкенда — вручную ничего
выполнять не нужно.

### Новые переменные в `.env` (все необязательные)
```bash
# Внешний IP сервера. Если не задать — определяется автоматически по маршруту
# наружу. Указывайте явно, только если сервер за NAT и «белый» адрес отличается.
AEGIS_HOST_IP=203.0.113.10

# Порт приватного реестра образов
REGISTRY_PORT=5000

# E-mail для уведомлений Let's Encrypt об истечении сертификатов
ACME_EMAIL=admin@example.com
```

### Что нужно знать про порты
* **Реестр образов** поднимается контейнером `aegis-registry` на порту `5000`
  (кнопка «Запустить реестр» на вкладке «Контейнерный реестр»).
* **Свои домены** обслуживает контейнер `aegis-caddy`, ему нужны порты **80 и 443**
  хоста: по 80 идёт HTTP-01 проверка Let's Encrypt, по 443 — сам HTTPS.
  Скрипт `bootstrap-host.sh` теперь отключает дефолтный сайт nginx, который
  раньше занимал порт 80. Если обновляете хост вручную, освободите порт так:
  ```bash
  sudo rm -f /etc/nginx/sites-enabled/default
  sudo nginx -t && sudo systemctl reload nginx
  ```
  Сам nginx остаётся работать — он обслуживает пулы балансировщика.
* Чтобы домены и сертификаты работали, порты 80/443 должны быть доступны из
  интернета, а A-запись домена — указывать на IP сервера.

## Проверка успешности установки:

1. **Проверьте статус контейнеров**:
   Убедитесь, что все службы запущены успешно (Up или healthy):
   ```bash
   docker compose ps
   ```

2. **Проверьте, что секреты зашифровались**:
   В логах бэкенда при старте должна появиться строка про шифрование старых секретов (если в базе были записи в открытом виде):
   ```bash
   docker compose logs backend | grep -i "секрет"
   ```
   А в самой базе пароли теперь хранятся с префиксом `enc:v1:`:
   ```bash
   docker compose exec db psql -U postgres -d aegis -c "SELECT left(password,10) FROM external_servers LIMIT 1;"
   ```
   *(Ожидается вывод вида `enc:v1:...`. Если серверов ещё не добавляли — таблица будет пустой, это нормально)*.

3. **Проверьте, что служебные порты закрыты снаружи**:
   С рабочей машины (не с сервера) попытка подключиться к базе по белому IP должна отклоняться:
   ```bash
   nc -vz <БЕЛЫЙ_IP_СЕРВЕРА> 5432   # ожидается "Connection refused" / timeout
   ```

4. **Проверьте доступность LVM из контейнера бэкенда**:
   ```bash
   docker compose exec backend pvdisplay
   ```
   *(Команда должна вывести информацию о физическом томе /dev/loop0 или аналогичном)*.

5. **Проверьте интерфейс**:
   Откройте веб-панель администратора, войдите под админом, откройте раздел баз данных или внешних серверов — пароли должны отображаться корректно (расшифровываются на лету).

## Развертывание Windows Server и настройка RDP:

В платформу Aegis добавлена возможность автоматического развертывания **Windows Server 2022**.

### 1. Создание и установка ВМ:
1. При создании виртуальной машины выберите **Windows Server** в качестве ОС.
2. После запуска откройте консоль **VNC** в панели Aegis.
3. Пройдите шаги установщика Windows. Когда программа спросит, куда устанавливать ОС, диск будет пуст. Нажмите **«Load Driver» -> «Browse»** (Загрузить драйвер -> Обзор).
4. Зайдите на CD-диск `virtio-win-...` (обычно диск `E:`), прокрутите вниз, найдите папку **`viostor`** -> папка **`2k22`** -> папка **`amd64`**. Нажмите **OK** и продолжите установку.

### 2. Установка драйверов и агента (внутри запущенной Windows):
1. Зайдите на рабочий стол Windows под пользователем `Administrator`.
2. Откройте проводник, перейдите на CD-диск `E:` (`virtio-win-...`) и запустите общий установщик:
   * **`virtio-win-gt-x64.msi`** (или `virtio-win_amd64.msi`).
3. Пройдите установку (кнопки Next -> Install). Это автоматически поднимет сеть (сетевая карта `NetKVM`), установит видеодрайвер для плавной графики и настроит Guest Agent для графиков в панели.

### 3. Включение удаленного доступа (RDP) и подключение:
1. В Windows откройте Поиск -> введите **«Remote Desktop settings»** -> включите переключатель **Enable Remote Desktop** в положение **On**.
2. В веб-панели Aegis в деталях вашей ВМ скопируйте строку подключения. Система сама рассчитает и пробросит внешний RDP-порт по формуле `33000 + последний октет IP ВМ`.
3. На вашем Mac откройте **Royal TSX**, установите бесплатный плагин **Remote Desktop (FreeRDP)** через Preferences -> Plugins, создайте подключение, указав IP сервера, проброшенный порт, логин `Administrator` и сгенерированный пароль. Подключение будет летать без тормозов!

## Дополнительная оптимизация хоста для HDD (BFQ и лимиты кэша):

Чтобы механический жесткий диск на хост-сервере работал максимально отзывчиво и **не вызывал полных зависаний ядра Linux** во время импорта тяжелых ВМ (например, Windows Server 2022 на 100 ГБ), необходимо ограничить размер грязного дискового кэша в оперативной памяти и переключить планировщик.

### 1. Настройка sysctl для предотвращения I/O Lockup (зависаний)
Мы заставим ядро Linux сбрасывать данные на диск гораздо раньше и мелкими порциями, исключая эффект "захлебывания" HDD:
```bash
# Применить настройки временно (до перезагрузки):
sudo sysctl -w vm.dirty_background_ratio=5
sudo sysctl -w vm.dirty_ratio=10

# Сохранить навсегда:
echo "vm.dirty_background_ratio=5" | sudo tee -a /etc/sysctl.d/99-aegis-hdd-tuning.conf
echo "vm.dirty_ratio=10" | sudo tee -a /etc/sysctl.d/99-aegis-hdd-tuning.conf
sudo sysctl --system
```

### 2. Включение Direct I/O для виртуального хранилища LVM
В файле `scripts/install-openebs-lvm.sh` мы добавили параметр `--direct-io=on` в службу монтирования loop-устройства. Это позволяет обходить двойное кэширование на хосте, снижая нагрузку на CPU и исключая сбои по памяти.
При повторном запуске скрипта службы:
```bash
sudo bash ./scripts/install-openebs-lvm.sh
```
служба пересоздастся с поддержкой Direct I/O.

### 3. Переключение планировщика диска на BFQ
Выполните на хост-сервере (где `sda` — имя вашего физического жесткого диска):
```bash
sudo sh -c 'echo bfq > /sys/block/sda/queue/scheduler'
```
*(Это предотвратит "подвисание" хоста во время активной записи данных виртуальными машинами).*
